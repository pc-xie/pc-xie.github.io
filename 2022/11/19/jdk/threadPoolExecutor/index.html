线程池

目的

  • 有大量异步任务的时候提升性能
  • 通过一系列参数对线程资源进行管理

构造线程池

参数说明

  • corePoolSize: 核心线程数
  • maximumPoolSize: 最大线程数, 通过ctl 去获取到, 其中包含了core 的值大小
  • keepAliveTime: 当线程数超过核心线程数(corePoolSize)，或者允许核心线程超时时，线程会使用此超时时间。
    否则，它们将永远等待新的工作。
    Timeout in nanoseconds for idle threads waiting for work.
    Threads use this timeout when there are more than corePoolSize
    present or if allowCoreThreadTimeOut. Otherwise they wait
    forever for new work.
  • unit: 空闲线程存活的时间单位
  • workQueue: 用于保存等待执行任务的队列
  • threadFactory: 用于创建线程的工厂
  • handler: 当任务队列满了以后, 用于何种策略去执行

线程池状态

  • 高3位表示状态, 后29表示个数
    为什么用高三位表示状态?
    因为线程池的状态有五种, RUNNING、SHUTDOWN、STOP、TIDYING、TERMINATED, 三位刚好可以表示

拒绝策略

常见的拒绝策略:

  1. AbortPolicy: 丢弃任务并抛出RejectedExecutionException异常。(默认拒绝策略)
  2. DiscardPolicy：丢弃任务，但是不抛出异常。
  3. DiscardOldestPolicy：丢弃队列最前面的任务，然后重新尝试执行任务。
  4. CallerRunsPolicy：由调用方线程处理该任务
    可以实现RejectedExecutionHandler的接口去进行自定义实现

shutdown

当调用shutdown()方法时，线程池会继续执行已提交的任务，但不再接受新的任务提交。
它会平缓地关闭线程池，即等待已提交的任务执行完成，然后逐渐停止线程池中的线程。
shutdown()方法会使线程池进入”正在关闭”的状态，可以通过isShutdown()方法来判断线程池是否处于关闭状态。
适用于希望让线程池中已提交的任务全部执行完毕，不接受新任务的情况，对于已提交的任务，可以调用awaitTermination()方法等待其执行完成。

interruptIdleWorkers

shutdownNow

当调用shutdownNow()方法时，线程池会尝试立即停止所有正在执行的任务，并且不再处理还未执行的任务队列。
它会尝试中断正在执行的任务，并返回尚未开始执行的任务列表。
shutdownNow()方法会使线程池进入”已终止”的状态，可以通过isTerminated()方法来判断线程池是否已经终止。
适用于希望尽快停止线程池并放弃尚未执行的任务的情况。
需要注意的是，无论是调用shutdown()还是shutdownNow()方法，都会停止线程池的接受新任务功能，但它们的行为和效果略有不同。具体选择哪种方法取决于你的需求和业务场景。

  • shutdown 和 shutdownNow 的区别

    • shutdown将运行状态改为shutdown, 当前正在执行和已经提交但是未被执行的任务都会被处理, 会在所有任务执行完成后进行关闭
    • shutdownNow 是将状态改为STOP, 中断所有线程, 返回为处理的任务
    • 一般情况下，建议先调用shutdown()方法，等待已提交的任务执行完成，然后再判断线程池是否已经终止。如果需要尽快停止线程池并放弃尚未执行的任务，可以在一段时间后（如等待一段时间后仍未终止），再调用shutdownNow()方法来强制停止线程池。
    • 总结：使用shutdown()方法时，线程池会平缓地关闭，允许已提交的任务执行完成；使用shutdownNow()方法时，线程池会立即停止并尝试中断正在执行的任务。根据需求选择合适的方法来关闭线程池。

    shutdown 适合温和的关闭方式, 等待已提交的任务执行完成
    shutdownNow 是一直强制的关闭方式, 立即中断所有活动的任务, 并返回尚未开始的任务

  • 线程内部异常处理
    Runnable 去进行submit 提交的:
    线程池的方式: 线程池会catch 到异常, 具体是否会抛出给主线程, 需要根据主线程是否实现afterExecute
    通过Runnable.run() 的方式则不会感知到异常
    Callable 去进行提交的时候, 则可以通过future 返回异常

直接说结论，需要分两种情况：

  • 使用execute()提交任务：当任务通过execute()提交到线程池并在执行过程中抛出异常时，如果这个异常没有在任务内被捕获，那么该异常会导致当前线程终止，并且异常会被打印到控制台或日志文件中。线程池会检测到这种线程终止，并创建一个新线程来替换它，从而保持配置的线程数不变。

  • 使用submit()提交任务：对于通过submit()提交的任务，如果在任务执行中发生异常，这个异常不会直接打印出来。相反，异常会被封装在由submit()返回的Future对象中。当调用Future.get()方法时，可以捕获到一个ExecutionException。在这种情况下，线程不会因为异常而终止，它会继续存在于线程池中，准备执行后续的任务。

线程池种类

ScheduledThreadPool

定时线程池。支持延迟执行和周期执行，适合定时任务、轮询、补偿任务。本质上是支持调度能力的线程池

FixedThreadPool

固定线程数线程池。核心线程数和最大线程数相同，适合比较稳定的任务处理场景。风险点是默认使用无界队列 LinkedBlockingQueue，任务堆积时可能导致 OOM。

CachedThreadPool

可缓存线程池。线程数理论上几乎无限，空闲线程会回收，适合大量短时异步任务。风险点是默认使用 SynchronousQueue，高并发下可能快速创建大量线程，容易把 CPU 和内存打满。

SingleThreadExecutor

单线程线程池。始终只有一个工作线程，适合串行执行、顺序性要求高的场景。风险点是吞吐能力低，前面任务慢会阻塞后续任务。

面试

什么是线程池？为什么要用线程池？

线程池本质上是对线程这种系统资源的复用和统一管理。如果每来一个任务就创建一个线程，线程创建和销毁的成本会很高，而且线程数失控时会带来上下文切换、内存占用和系统负载飙升的问题。线程池的价值主要有三点：第一，复用线程，降低创建销毁成本；第二，控制并发度，防止资源被打满；第三，便于统一做队列、拒绝策略、监控和治理

核心参数

corePoolSize 核心线程数，
maximumPoolSize 最大线程数，
keepAliveTime 非核心线程空闲存活时间，
unit 时间单位，
workQueue 任务队列，
threadFactory 线程工厂，
RejectedExecutionHandler 拒绝策略

线程池执行任务的流程是什么

  1. 如果运行中的线程数小于核心线程数，优先创建核心线程执行任务；
  2. 如果核心线程都在忙，就先尝试把任务放进阻塞队列；
  3. 如果队列满了，并且当前线程数还没到最大线程数，就创建非核心线程处理；
  4. 如果队列也满了，线程数也到上限了，就触发拒绝策略。
    所以线程池不是一上来就不断创建线程，而是在线程数和队列之间做平衡。

常见阻塞队列有哪些？怎么理解

ArrayBlockingQueue：有界数组队列，容量固定，适合明确控制堆积量；
LinkedBlockingQueue：链表队列，默认容量很大，如果不手动设上限容易堆积；
SynchronousQueue：不存储元素，来一个任务必须立刻交给线程处理，常见于 CachedThreadPool；
PriorityBlockingQueue：支持优先级。
生产里我更偏向有界队列，因为这样才能真正控制风险。

常见拒绝策略

AbortPolicy：直接抛异常，默认策略；
CallerRunsPolicy：由提交任务的线程自己执行，能起到反压效果；
DiscardPolicy：直接丢弃，不报错；
DiscardOldestPolicy：丢弃队列里最老的任务，再尝试提交当前任务。
如果是核心链路，我通常不会默认静默丢弃，而是结合业务场景选择抛错、降级或者记录告警

如何监控线程池是否健康

线程池和并发治理重点监控

线程池监控我一般会分成六类来看。
第一类是资源类指标，比如 poolSize、activeCount、maximumPoolSize，主要看线程资源用了多少；
第二类是队列类指标，比如 queue.size 和 remainingCapacity，主要看任务有没有堆积；
第三类是吞吐类指标，比如 taskCount 和 completedTaskCount，看处理能力是否跟得上提交速度；
第四类是异常类指标，比如拒绝次数、异常数和超时数，判断线程池是不是已经扛不住；
第五类是时延类指标，比如任务执行耗时和排队耗时，用来区分慢点是在执行还是在排队；
第六类是饱和度指标，比如线程饱和度、队列饱和度和拒绝率，这类指标更适合直接判断线程池当前的健康状态

- 线程活跃度 = activeCount / poolSize
- 线程饱和度 = activeCount / maximumPoolSize
- 队列饱和度 = queue.size / 队列总容量
- 拒绝率 = rejectedCount / taskCount

这个项目里最该盯的 5 个指标

  1. 线程池利用率
    这是最直接的饱和度指标，能最快看出某一类三方是不是把线程资源吃满了。
  2. 队列堆积
    线程池没拒绝不代表没问题，队列持续增长往往是 RT 恶化前最早的信号。
  3. rejected + sem.rejected
    一个代表本机资源打满，一个代表下游保护生效，这两个指标能快速区分问题是在内部还是外部依赖。
  4. pool.task.exec + downstream.rt
    两个指标要结合看，才能判断是线程真正忙于业务计算，还是下游广告源慢导致整体链路变长。
  5. callback.timeout + aggregate.success.ratio
    异步化之后必须盯回调超时和最终聚合成功率，否则线程池指标看着正常，结果链路可能已经在悄悄降级。

线程池参数怎么定

我一般不会拍脑袋定线程池参数，而是先用 Little’s Law 算一个理论并发基线，再结合任务类型、队列策略、超时设置、机器资源和压测结果去做调整。公式可以理解成：

并发数 = QPS × 平均线程占用时间

比如单机 QPS 是 4500，平均线程占用时间是 10ms，那么理论并发基线就是 4500 × 0.01 = 45。但这个 45 只是起点，不是最终线程数。最终还要看任务是 CPU 密集还是 IO 密集、是否允许排队、队列容量多大、有没有超时和快速失败，以及高峰流量下的抖动情况。我的习惯是先算理论值，再加冗余，再通过压测和监控验证，最后确定 corePoolSize、maximumPoolSize 和 queue 的组合。

CPU密集型：corePoolSize = CPU核数 + 1（避免过多线程竞争CPU）
IO密集型：corePoolSize = CPU核数 x 2（或更高，具体看IO等待时间）

为什么不建议直接用 Executors

因为 Executors 提供的快捷工厂方法很多默认参数在生产环境不安全。比如 FixedThreadPool 和 SingleThreadExecutor 默认使用无界 LinkedBlockingQueue，任务堆积时可能导致 OOM；CachedThreadPool 的最大线程数接近无上限，高并发下可能快速创建大量线程，把 CPU 和内存打满。所以生产环境更推荐直接 new ThreadPoolExecutor，显式指定线程数、队列容量、线程工厂和拒绝策略，让线程池行为可控。

有界队列和无界队列怎么选

生产环境我更偏向有界队列。无界队列的好处是短期内不容易触发拒绝，但代价是任务可能无限堆积，导致 RT 变长、内存上涨，而且很多时候 maximumPoolSize 也失去意义。有界队列虽然会更早暴露容量问题，但它能把风险限制住，逼着系统通过拒绝、降级、限流或者扩容来处理问题。我的理解是，无界队列是在隐藏问题，有界队列是在控制问题。

线程池里的任务互相等待会出什么问题

可能直接导致线程池进行假死
这是线程池里非常典型的风险。如果一个任务提交到线程池后，又同步等待同一个线程池里的其他任务结果，比如在任务里调用 Future.get()
====就可能出现线程饥饿甚至假死。因为线程都被前面的任务占住了，后面的依赖任务没有线程执行，前面的任务又一直在等后面的结果，最后整个线程池卡住。
解决思路一般有三种：第一，避免同池同步等待；第二，拆线程池做隔离；第三，改成异步编排或者设置超时，避免无限等待。

为什么线程池隔离很重要

因为不同业务、不同下游的耗时模型和风险完全不一样。如果所有任务共用一个线程池，一个慢接口或者异常下游就可能把线程全部占满，最终拖垮整条链路。线程池隔离本质上是资源隔离，把故障影响范围限制在局部。比如高频短任务和低频慢任务应该拆开，不同三方依赖也应该拆开。线程池解决的不只是并发执行问题，更重要的是控制故障扩散。

execute 和 submit 的区别，以及异常怎么处理

execute() 只接收 Runnable，没有返回值；
submit() 可以提交 Runnable 或 Callable，会返回 Future，适合需要拿结果、取消任务或感知异常的场景。

异常处理上，两者差别很大：

  1. execute() 提交的任务如果抛异常，如果异常没有进行补货, 那会直接导致当前的worker 进行退出, 线程池感知这个worker 是异常结束的, 如果线程池还需要维持核心线程出或者队列里面还有任务, 那会重新补一个线程, 确保整体的处理能力不被长期削弱。
  2. submit() 提交的任务如果抛异常，异常不会直接抛到调用方，而是被封装进 Future，只有在调用 get() 时才会拿到 ExecutionException，如果没有调用get 的时候异常会被吞掉

所以如果只是 fire-and-forget 类型任务，可以用 execute()；如果要拿结果或者感知任务失败，用 submit() 更合适。但不管哪种方式，生产里都不能只依赖默认行为，最好在任务内部做好异常收口、日志和监控。
