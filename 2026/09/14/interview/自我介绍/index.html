传音

项目背景

原来的广告展示模式是静态素材预下发，运营需要提前把文案、图片等内容配置好，等客户端下次拉取后才能生效。后来业务希望提升实时性，所以架构升级成了服务端实时请求多个下游三方获取内容，动态返回最终广告信息，不再依赖静态素材预下发。这样改造之后，广告配置和内容都可以实时生效。

在这种多下游实时聚合场景下，链路对下游依赖非常强。改造前聚合链路 99 线耗时在 10 秒，任何一个下游的慢响应或者抖动，都会直接影响最终广告展示效果和收益。

做了 多下游并行聚合、线程池隔离、异步 I/O、熔断缓存和配置热更新

并行聚合是怎么做的:

====

并行聚合的实现上，核心分成以下几个部分。

==第一步是任务拆分，入口请求进来之后，我们会先根据区域配置、广告源配置以及请求上下文，解析出当前请求需要调用哪些三方广告源，然后把它拆成多个相互独立、没有前后依赖关系的子任务。

==第二步是并行执行，给下游发起并发请求。
因为这些子任务之间没有依赖，所以不会再像以前一样串行调用，而是直接并发发起请求。这样整体 RT 理论上就会从“多个下游耗时累加”收敛到“最慢一路下游的耗时”。

==第三步是资源隔离，将任务放到不同的线程池中处理。
这里我没有把所有任务放到同一个线程池，而是按 A/B/C 三类特性拆到不同线程池中处理。因为不同广告源的耗时和流量特征差异很大，如果共用一个线程池，一旦某一路慢请求变多，就会把其他正常流量拖垮。

==第四步是并发控制和超时治理。
在线程池隔离之外，我又针对每类广告源加了 Semaphore 并发配额控制，限制对下游的最大并发，超过阈值就直接降级，避免请求堆积。同时针对不同广告源配置差异化超时时间，任一路超时后直接结束，不阻塞其他并行任务。

==第五步是结果聚合。等各路任务返回后，聚合层会把成功返回的素材结果统一组装。
如果某一路失败或者超时，不会让整个请求直接失败，而是尽量保留其他成功结果返回给客户端，避免局部故障放大成整体无结果。

3. 为什么还要做三个线程池？

这里其实是这个项目比较重要的一个架构点。
我们并不是简单地把所有三方请求全部扔到一个线程池里。
因为不同三方的特点不一样。
比如：

  • A 类：高频、RT 比较短、主要追求吞吐
  • B 类：中等耗时
  • C 类：RT 比较长，而且长尾比较明显
    如果全部使用一个线程池，那么 C 类三方出现大量慢请求的时候，就可能把线程池里的资源全部占满。
    最终导致：

    一个慢三方把其他正常三方也拖慢。
    所以我们按照三方来源的特性，把它们划分成了 A/B/C 三类线程池进行隔离。
    这样即使 C 类三方出现大量慢请求，也不会直接把 A、B 两类请求的线程资源全部占用。

4. 线程池参数怎么设计？

这里我建议你面试的时候重点讲 Little’s Law，这个会让你的回答从“我调了几个参数”提升到“我有容量模型”。
我们的峰值场景大概按照单 Pod 4500~4600 QPS 来进行容量设计。
同时根据实际压测和监控，我们发现真正占用线程池资源的平均时间并不是完整的下游 RT，而是线程池任务在发送请求以及处理相关逻辑上的平均资源占用时间，大概按照 10ms，也就是 0.01s 来进行线程资源估算。
这里使用 Little’s Law：

并发数 ≈ QPS × 平均资源占用时间
比如按照 4500 QPS：
4500 × 0.01 = 45
也就是说理论上的平均并发资源占用大约是 45。
然后我们再根据实际流量、不同来源的流量占比以及安全冗余系数进行容量放大，最终确定三个线程池的 core/max、队列以及 Semaphore 参数。

这里的核心思想不是“拍脑袋设置 64、128”，而是：

根据峰值 QPS → 按来源流量比例拆分 → 根据任务资源占用时间计算并发 → 再增加安全冗余 → 最终确定线程池和 Semaphore 参数。

6. 为什么还需要 Semaphore？

这个地方你面试的时候可以重点说。
线程池解决的是线程资源隔离问题，Semaphore解决的是下游请求并发数控制问题。
比如 C 类三方平均 RT 比较高，而且长尾明显。
如果单纯依赖线程池，在流量突然升高或者三方 RT 突然变长的时候，可能会出现大量请求堆积。
所以我们又在三方调用层增加了 Semaphore。
例如：

通过 Semaphore 控制同时发送到某一类三方的请求数量。
超过并发阈值之后直接拒绝或者快速降级，而不是无限制地把请求压给三方。
这样能够避免：

流量突增 → 请求堆积 → 线程池耗尽 → GC增加 → RT升高 → 服务雪崩
形成这种级联问题。

7. 超时和降级

另外我们对不同类型的三方设置了不同的 timeout。
因为 A/B/C 的 RT 特征不同，所以不能统一设置一个超时时间。
例如：

  • A：150ms
  • B：500ms
  • C：800ms
    如果某个三方超过 timeout，就直接进行降级。
    也就是说：

    一个三方失败，不影响其他三方正常返回。
    最后聚合层只把已经成功返回的广告素材进行统一聚合。

第一，接口 P99：

从 10 秒降低到 1 秒左右。
第二，Young GC：

并行聚合 + 线程池隔离 + Semaphore 并发控制 + 超时控制 + 快速失败 + 降级 + 配置动态生效。

异步IO 是怎么做的:

我们这个广告聚合服务入口 QPS 约 900，并行调用多方广告源之后，下游总 QPS 会放大到 4600。改造前使用同步 HTTP Client，业务线程在等待三方网络响应时会阻塞。一旦下游 RT 抖动，大量业务线程卡在 IO 等待，线程池资源很容易耗尽，引发服务稳定性问题。

====所以我将同步客户端改造成基于 Netty 的异步非阻塞 IO 模型。业务线程只负责发起任务，网络读写交给 Netty EventLoop 处理，通过回调接收结果，实现计算线程和网络 IO 的隔离，少量线程就可以支撑大量并发请求。
但异步模型会带来新风险：请求发送速度变快，如果没有约束，会造成 Socket 连接数暴涨，直接压垮下游三方。因此我们在异步调用链路增加 Semaphore 做单机维度的下游并发配额控制。针对每个广告源独立限制最大并发，超过阈值直接快速失败并触发降级，避免流量失控引发级联故障。

异步 IO + Semaphore，和前面多线程池隔离方案是什么关系？

答：
线程池是隔离本机内不同广告源的业务任务线程，解决内部资源争抢；
异步 IO 释放线程，提升单机吞吐；
Semaphore 是管控对外下游的并发请求量。
三者配合：线程池隔离内部资源，异步 IO 提升线程利用率，Semaphore 保护下游依赖，多层防护。

不用线程池, 只用netty问题

因为一旦不用线程池，业务处理就会和 I/O 线程耦合在一起。正常情况下这些逻辑可能很轻，但如果某个下游结果处理出现波动，就可能把 EventLoop 占住，影响同线程上其他连接和请求的处理。

另外，线程池更重要的作用其实不是单纯执行任务，而是做业务隔离。

所以我们的做法是让 Netty 负责网络层的异步读写，把结果处理这些逻辑放到线程池里。也就是说，异步 I/O 解决的是等待问题，线程池解决的是资源隔离问题，这两者不能互相替代。

异步回调有什么坑，怎么处理？

答：主要风险是回调异常、超时不触发带来内存泄漏。我们给所有异步请求统一设置超时，增加回调埋点监控成功、超时、异常指标，同时每个下游使用独立连接池，防止单个三方故障污染全局连接资源。

Sempahore 实现原理

通过AQS 去进行实现, Semaphore 内部有一个共享的 state,表示剩余的 permit 数量。acquire 的时候通过 CAS 尝试把 state 减一,减成功就拿到许可;减不了就阻塞等待(或快速失败),等待的线程会被放进 AQS 的队列里;release 时把 state 加一,唤醒等待队列里的线程。因为高并发下可能有很多线程同时来竞争 permit,所以必须用 CAS 保证修改 state 的原子性,避免并发安全问题, 在进行tryAcquire 的时候去进行处理。

Sempahore 分类

线程池按照三类任务特征分成 A/B/C 三类,用三个线程池做资源隔离是合理的。但 Semaphore 更应该细化到每一个具体三方,比如五个三方就各自有独立的并发控制器,防止某个三方流量突增把同一线程池里的其他三方也拖垮。

GC 优化怎么做的:

===并行改造后下游等待时间降了，但 Young GC 最高到 2 秒。先排查内存泄漏，Old 区稳定排除老年代问题，判断是 Young 区短对象过多。用 Arthas Profiler 定位，热点在三方数据序列化反序列化，还有每次克隆广告曝光模板 —— 并行后每次任务都克隆，产生大量临时对象。优化时把模板改成只读，去掉克隆，每个请求只传必要上下文，任务完成后统一填充模板，减少 90% 以上中间对象，最终 Young GC 降到 10 毫秒。

并行化改造之后，整体下游等待时间虽然降下来了，但我们观察到 Young GC 的 Pause 最高到了 2 秒。这个时候我先没有急着去调 JVM 参数，而是先判断问题性质。

第一步先排除内存泄漏，因为当时 Old 区整体比较稳定，没有明显持续上涨，所以判断主要压力不在老年代，而是在Young 区对象分配过快、回收压力过大。

第二步我用 Arthas 的 profiler 去看 allocation flame graph，发现热点主要集中在SerializationUtils.clone，以及 JSON 反序列化之后的一些对象装配和 copy 操作。结合链路分析后发现，问题本质上是并行化之后，多路结果会在同一时间窗口内同时存在，导致请求过程中的临时对象分配量明显增加，从而把Young GC 压力放大了。

所以这个问题我没有选择简单去调大堆或者只改 GC 参数，因为那只能延后问题，不是从根因上解决。我的处理方式是从对象生命周期和数据结构设计上入手：把模板改成只读，去掉 clone；在创建任务时只传必要的 contextHolder；等所有任务执行结束后，再统一对模板数据做填充。这样一次请求内只保留一份骨架数据和一份下游结果引用，避免了大量中间对象 copy。

改完之后，Young GC Pause 从 2 秒左右降到了 200 毫秒左右。对我来说，这次优化的重点不是 JVM 参数调优本身，而是通过分配热点分析，把问题定位到对象模型和装配方式上，再从代码结构层面把分配速率降下来

基于配置监听的变更感知手段是怎么做的

我们原来是 Spring Boot 定时任务每 5 分钟轮询数据库,实时性较差。后来改成“事件通知+ 主动拉取+ 定时轮询兜底”的方案。运营修改素材配置时先落库,然后更新配置中心的版本文件。服务端监听到变更事件后,再主动拉取数据库的最新配置写入本地。同时保留原有 5 分钟的定时任务作为兜底,以防事件丢失。这样正常情况下可以做到近似秒级感知配置变化,同时又不完全依赖事件机制,可靠性也有保证。

分级熔断与缓存处理是怎么做的:

================================
我们当时做分级熔断和缓存兜底，核心目标是两点：第一，在下游部分异常时尽量保住广告返回结果和收益；第二，避免下游故障直接放大成整体链路不可用。

做法上，我们基于 10 秒滑动窗口统计每个下游的失败率，并按失败率分成四级：正常状态正常转发；轻微异常时继续请求下游，同时把成功结果写入 Redis 预热缓存；中度异常时，请求失败优先读缓存兜底；严重异常时直接强熔断，正常流量不再打下游，只保留少量探针请求检测恢复情况，恢复后再分阶段放量。
这样做的好处是，单个广告源出问题时，不会直接把整条聚合链路拖垮，同时还能尽量保住曝光和收益。
================================

具体实现上，我们会基于滑动窗口去持续评估每个下游广告源的健康状态。以 10 秒为一个统计窗口，窗口内记录请求总数、成功数和失败数，并用失败次数 / 总请求数计算当前失败率。基于这个失败率，我们把下游健康状态分成 4 个 等级。

L0 是正常状态，也就是失败率低于 20%。这个阶段说明下游整体稳定，请求正常转发，不做额外干预。

L1 是轻微异常，失败率在 20% 到 50% 之间。这个阶段我们认为下游开始有波动，但还没有严重影响整体可用性，所以请求仍然正常转发。同时把成功返回的内容写入 Redis，作为后续进一步异常时的兜底数据。缓存维度会按providerId + 国家 + 语言 + 品牌 组合，尽量保证命中结果和用户请求场景匹配。

L2 是中度异常，失败率在 50% 到 80% 之间。这个阶段我们仍然会尝试正常请求下游，但如果调用失败，就不再直接把失败暴露给上层，而是优先读取 Redis 缓存做兜底。如果缓存有数据就返回缓存，没有缓存就直接返回空结果或者进入上层降级逻辑。这样可以在下游不稳定时尽量保住返回结果。

L3 是严重异常，也就是失败率超过 80%。这时我们认为下游已经接近不可用，继续大量转发只会放大故障，所以会进入强熔断状态，正常流量不再直接打到下游，而是优先读取缓存返回。同时为了避免永久熔断，我们会开启探针恢复机制，比如每秒放 5 个探针请求去检测下游是否恢复。当探针结果连续恢复正常后，不会一下子把全部流量切回去，而是按 5%、20%、50%、80%、100% 这样的节奏逐步放量，避免下游刚恢复时再次被流量冲垮。

所以这套机制本质上不是简单的“失败就熔断”，而是通过滑动窗口做健康评估，再结合不同故障等级选择不同的处理策略：轻微异常时做缓存预热，中度异常时失败读缓存，严重异常时强熔断加探针恢复。这样既能控制故障扩散，也能尽量保住广告曝光和收益

方案的取舍

这个方案最大的取舍，是牺牲一部分实时性和实现复杂度，换下游异常场景下的整体可用性和收益稳定性。比如进入中重度异常后，我们允许一部分请求直接走缓存，这样返回内容可能不是绝对最新的，但能尽量保住曝光和填充，不至于因为三方故障导致整体无结果。另一方面，分级熔断、探针恢复、渐进放量这些机制也会增加系统复杂度，但它的价值是能把故障控制得更细，不会出现要么全量打下游、要么一刀切全熔断的情况。
所以本质上，这个方案是在收益链路里用一定的实时性损失和系统复杂度，换更强的故障收敛能力和整体稳定性

追问 1：为什么选用 10 秒滑动窗口，不是更长或者更短？

答：窗口大小是权衡灵敏度和抗抖动。窗口太短，少量突增失败就会误判熔断；窗口太长，无法快速感知下游故障。10 秒窗口既能平滑瞬时毛刺，又可以较快捕捉下游持续恶化的故障，适配我们广告素材调用的 RT 特征。

追问 2：滑动窗口是怎么实现的？是环形桶滑动窗口吗？

答：采用分桶滑动窗口，把 10 秒拆成多个时间桶，每个桶独立统计成功、失败计数。时间滑动时淘汰过期桶数据，只保留最近 10 秒的统计，避免单个大窗口内存开销，同时保证统计的时效性。

追问 3：阶梯恢复为什么是这几个比例？

答：阶梯式放量是为了渐进验证下游恢复能力。从小流量 5% 开始观察下游指标，确认稳定后再提升流量比例，一旦在某个阶段失败率再次升高，立刻停止放量并回退到缓存模式，防止故障反复。

追问 4：失败率计算的时候，有没有考虑请求量太少的场景（低基数误判）？

答：这里有个保护机制，如果窗口内总请求量低于最小阈值，不参与失败率计算，防止少量请求的随机失败，误触发降级，这是防止熔断误触发的保护逻辑。

限流怎么做的

我们做限流时，采用的是单机限流，而不是集中式的集群限流。核心原因是网关本身就是流量入口，我们更看重链路上的稳定性，不希望为了限流再额外引入 Sentinel 这类强依赖。否则一旦依赖异常，限流能力本身可能反过来放大网关故障。

具体实现上，我们基于滑动窗口做请求统计，窗口里统计的是单位时间内的请求数，限流 key 支持按业务场景自定义，比如可以按商户id。因为我们线上 Pod 流量是均衡的，所以整体上也可以实现限流的效果。

所以这套方案本质上是在准确性和系统复杂度之间做取舍。我们没有追求绝对精确的全局限流，而是优先保证网关链路稳定。

为什么用滑动窗口

我们当时选择滑动窗口，主要是因为它更适合按时间段控制总流量的场景。我们的目标是判断某一段时间内请求量有没有超标。

如果是令牌桶，它更适合平时流量比较平稳，但偶尔允许短时间流量比较大。
如果是漏桶，它更适合不管上游瞬时进来多少请求，下游看到的流量都比较均匀。

而我们当时更关注一段时间内的总量控制。所以最终选择了滑动窗口。

网关的整体架构是什么样的

我们这个网关整体上可以分成三层：控制面、配置存储与分发层，以及数据面

控制面主要是控制台，负责路由、限流、鉴权、权重等规则配置，同时也承接外部系统的一些配置推送。配置变更后会先持久化到数据库，再通过 ZooKeeper 做配置通知和动态分发。网关服务节点作为数据面，会监听 ZooKeeper 上的配置变化，并刷新本地配置缓存。这些配置既包括路由规则，也包括后端实例列表、权重分组、限流规则等运行时数据。

在请求链路上，外部请求会先经过 WAF 和 SLB，再进入网关。网关收到请求后，会先根据 Host 和 Path 做路由匹配，确定目标应用，然后再结合应用对应的实例列表、权重和分组规则，选择具体的后端实例进行转发。在这个过程中，网关还会做鉴权、限流、签名校验等通用治理逻辑。

和偏通用型的网关相比，我们这个网关会更贴近业务场景。除了常规的路由和转发能力外，还会解析请求体里的业务字段来做验签和更细粒度的限流。比如公司内部很多场景会约定商户 ID 放在 Body 第一层，所以我们支持基于这个字段做流量治理。但这里也有明确取舍，我们没有支持任意层级的嵌套解析，因为那样会明显增加解析开销、规则复杂度和维护成本，所以只支持约定格式下的有限解析能力

tomcat 换成netty

当时网关流量上来以后，CPU 负载和接口 RT 都明显恶化。我通过 vmstat 观察到上下文切换很高，结合线程模型判断，主要问题是 Tomcat 阻塞式处理下线程数膨胀，CPU 大量消耗在线程切换上，线程池打满后请求还会排队，所以 RT 会持续变差。

后来我推动把接入层从 Tomcat 切到 Netty，改成基于 NIO 的异步事件驱动模型，用少量 EventLoop 线程处理大量连接和 I/O，减少线程切换和阻塞等待。虽然异步模型复杂度更高，但对网关这种核心入口来说，性能和稳定性的收益更大

当时压测和线上高峰期观测，通过 vmstat 监控发现，流量上涨后 CPU 负载飙升，接口 RT 显著恶化。

在请求量大的情况下：

1. CPU 负载发现急剧上升
2. 整体请求的耗时一下子上来了

排查原因：

vmstat 用于观测整机 CPU、内存、上下文切换等系统指标，核心看 cs 上下文切换、us/sy CPU、r 就绪队列。
我当时用 `vmstat 1`，每秒采集一次数据。在流量上涨时，观测到 cs 暴涨、sy 升高，判断是大量线程带来频繁上下文切换。后续搭配 pidstat，定位到是 Tomcat 进程产生大量线程切换开销。

1. 由于线程开的太多了，上下文切换比较频繁
2. 有一些请求会由于 tomcat 阻塞住了，导致外部请求有堆积。将允许的线程数开大的话，会导致线程切换更加频繁

解决办法：将网络框架换成 netty 去处理。

1. tomcat 相比较于 netty 的线程模型

   tomcat 采用的是多线程阻塞模式，每个请求对应到一个线程上去。在请求量变多的情况下，会导致线程数急剧上涨，从而带来线程上下文的开销；同时线程池中的核心线程数到了上限后，后面过来的请求就需要等待。
   对比 netty 的线程模型，netty 采用了基于 NIO 和事件异步驱动的方式来处理，只需要通过少量的线程和 EventLoop 机制就可以处理大量的并发请求。它不会为每个请求创建一个线程，通过少量的线程来管理多个 IO 事件，从而极大避免了线程的上下文切换。

2. IO 模型：tomcat 采用的是 blockingIO，netty 采用的是 NIO。

取舍：

复杂度上升。同步模型代码简单，链路直观；异步模型在超时控制、异常传播、上下文传递、日志排查上都更复杂。我们的取舍是，网关是统一流量入口，稳定性和吞吐优先级高于实现复杂度，所以愿意接受更高的研发复杂度，换更高的性能上限和更好的资源利用率。

Tomcat 现在也支持 NIO，为什么不直接使用 Tomcat 的 NIO 模式，而是整体换成 Netty？

答：Tomcat 的 NIO 只是底层 IO 改成 NIO，上层仍然是一请求一线程模型。即使 IO 是非阻塞，业务处理依然要占用独立线程，并发上来还是会产生大量线程，上下文切换的核心问题没有解决。Netty 的事件驱动模型可以做到业务异步化，不需要每个请求独占线程，这是本质差异。

迁移 Netty 有没有遇到什么坑？

答：最大的挑战是异步编程模型带来的回调复杂度，需要妥善处理异常、超时、内存泄漏。同步代码的异常链路很直观，而异步回调如果处理不当，容易丢失异常，或者回调不触发造成内存堆积。我们增加统一回调埋点、异步请求强制超时机制来兜底。

EventLoop 线程池怎么配置？EventLoop 能不能执行业务逻辑？

答：EventLoop 线程是 IO 线程，绝对不能执行耗时业务逻辑，否则会阻塞 IO 事件处理。业务计算、下游调用任务会提交到独立业务线程池，和 EventLoop IO 线程做隔离，保证 IO 事件处理不被业务阻塞。

为什么tomcat 要用那么多线程去进行处理, 而netty 用几个线程就可以去完成同样的事情

1. IO 模型上的差异
    1. tomcat 是基于blocking IO 来实现的, 每个HTTP 请求创建一个独立的线程来做的, 如果线程被阻塞住了, 会导致无法处理其他任务. 为了保证高并发下可以去处理, tomcat 需要在配置足够多的线程去预先准备好, 但是线程数过多后会导致线程的上下文切换和内存开销, netty 是基于 NIO 和 事件驱动机制来做的, 不用为每个请求去创建一个线程去处理
1. 事件驱动的设计
    因为netty 是基于reactor 的事件驱动模型,worker 不处理整个请求的生命周期, 只响应或底层发出的网络事件, 使得只有事件触发的时候才去执行任务, 而不是阻塞等待
2. 非阻塞 I/O
    netty 使用的NIO 为非阻塞IO, selector 机制: 通过NIO的selector的机制, netty 可以让worker 线程管理多个channel, 当selector监听到某个channel 有IO 事件的时候, 该线程才会去处理这个channel, 在没有事件时, 线程会去监听而不被阻塞
3. 任务划分与分离
    bossGroup 和 workerGroup 的职责分离, bossGroup 专门处理连接的建立和关闭, 而worker Group 专注于处理已建立的连接的读写操作. 从而避免了线程资源的抢占
4. 避免线程上下文的切换. 
    IO 的多路复用技术, 可以让一个线程监听多个channel 上的事件, 当channel 准备好读写的时候, 线程可以立即处理, 从而显著减少了线程数量

netty 的几个概念

EventLoop

EventLoop 本质上是 Netty 的事件循环执行器，通常会绑定一个线程，负责轮询 IO 事件，同时执行普通任务和定时任务。一个 EventLoop 可以管理多个 Channel，但一个 Channel 在生命周期内只会绑定到一个EventLoop 上。这样设计的好处是，同一条连接上的 IO 事件和任务处理都在同一个线程里串行执行，可以减少并发竞争和加锁开销。
eventLoop 如何管理多Channel 不卡顿: 一个eventloop 通过selector 监听多个channel 的 io 事件,只有当Channel 有可读可写事件才会触发再去进行处理, 同时netty 的 IO 逻辑相对轻量, 只要把耗时长的操作进行剥离, 就可以实现对大量 channel 的管理

Channel

Channel 是 Netty 对网络连接或者 IO 通道的抽象。比如服务端监听端口时会有 ServerSocketChannel，真正建立连接后会有对应的 SocketChannel。Channel 负责承载这条连接上的读写、连接状态、关闭等操作，可以理解成网络通信的载体。
可以通过Channel 中的 attr 去进行绑定一些数据

ChannelPipeline

ChannelPipeline 可以理解成 Channel 对应的一条处理链。每个 Channel 都会绑定一个 Pipeline，网络数据进来之后，会沿着这条链依次经过多个 Handler 做处理；数据写出去时，也会沿着这条链反向经过一系列Handler。它的作用就是把编解码、协议处理、业务逻辑、异常处理这些步骤串起来，形成职责清晰的处理流程。

ChannelHandler

ChannelHandler 是挂在 Pipeline 上的具体处理器，用来处理某一类事件或者某一段逻辑。比如有的 Handler负责解码，有的负责编码，有的负责业务逻辑，有的负责异常处理。不同的 Handler 各自职责单一，组合起来完成整条链路的处理。

如果把它们关系串起来理解的话：
  • Channel 是一条连接或者一个 IO 通道；
  • EventLoop 负责驱动这个 Channel 上的 IO 事件和任务执行；
  • ChannelPipeline 是这个 Channel 的处理链；
  • ChannelHandler 是处理链上的具体处理单元。

所以一个请求进来之后，通常是 EventLoop 先感知到 Channel 上有 IO 事件，再驱动这个 Channel 对应的
Pipeline 去处理，而具体的编解码、业务逻辑、异常处理，则是由 Pipeline 上的各个 Handler 分工完成的。

后端连接去 池化 处理

具体实现上做了3个事情

  1. 根据后端实例维度建立连接池, 优先复用已有的连接, 而不是每次创建新的连接
  2. 对连接池设置最大连接数、空闲回收和等待策略, 避免在突发流量下无限增长
  3. 增加心跳和实现连接剔除机制, 确保连接池里面的连接都是可用的. 这样降低了建连的成本, 也提升了网关的稳定性和成功率

好处

1. 减少连接的创建和销毁带来的开销
    1.1 每次创建新的连接都是需要建立TCP 链接的握手等操作, 连接池通过复用的连接, 避免了频繁的创建和销毁连接的开销, 同时可以降低资源的消耗
2. 避免资源耗尽
    2.1 连接池允许多个请求同时使用共存的连接, 同时会对后端机器、整个应用级别有连接数的限制, 防止资源的耗尽
3. 优化响应时间
    3.1 通过对连接的复用, 应用不需要等待新连接的创建或者释放, 提高了响应速度
4. 连接池中的心跳检测机制, 可以及时的将无效的连接去进行剔除, 提高网关转发请求的一个成功率

请求去做全异步化

所谓全局异步化, 本质上就是将原来同步阻塞的请求转发链路, 改成了基于 netty 的异步事件驱动模型. 请求进入网关后, 前后端网络读写都不占用线程池同步等待, 而是通过异步发送和回掉处理。 这样结果最大的价值就是减少了线程阻塞. 提高了连接利用率和单机吞吐能力

这样可以带来什么好处

1. 提高网关自身的稳定性
2. 防止由于后端应用处理耗时上涨, 将整体性能拖垮

集群拆分可以带来什么好处

实现

这个项目不是简单把机器拆开，而是一次流量和资源隔离改造。分析接入网关的不同应用流量特征，比如交易类、长耗时类、任务调度类，再根据 QPS、RT、资源消耗等定义拆分原则，把高风险、高波动业务从原来的大集群里拆出来。

拆分过程中，我一方面做容量评估和路由改造，确保不同应用能稳定落到对应小集群；另一方面会和 NOC 一起推进部署和接入关系调整。上线时不是一次性切换，而是按应用分批灰度迁移，同时监控 RT、错误率和资源使用情况，并准备回滚方案。最终实现的是业务之间的资源隔离，降低了流量争抢和故障扩散。

  1. 先做业务和流量分层: 分析接入网关的不同应用类型和流量特征，比如交易类、长耗时类、任务类、Portal 类、对外开放类，重点看 QPS、RT、峰值波动、资源消耗和故障影响面
  2. 定义拆分原则：按业务属性、流量模型和稳定性诉求来划分集群，核心目标是让高风险、高波动、高资源消耗的流量和其他业务隔离开，避免相互争抢
  3. 做容量评估和资源规划: 根据每类应用的峰值流量、机器规格、冗余要求，评估每个小集群需要多少实例、连接数和线程资源，确保拆分后不是把大问题拆成多个小瓶颈
  4. 改造路由和接入关系: 把原来统一接入大集群的应用，调整成按应用或业务类型路由到对应的小集群。这里通常会涉及网关路由规则、注册信息、发布配置和调用入口的调整
  5. 和 NOC/运维一起推进网络和部署改造: 我会和 NOC 一起推进应用接入关系、机器资源、部署拓扑和流量切换方案，保证改造能真正落地
  6. 分批灰度迁: 按应用、按流量比例逐步迁移，先迁风险低的，再迁核心流量，同时观察 RT、错误率、连接数、CPU、内存等指标
  7. 做好回滚和兜底: 每次迁移前都准备回切方案，确保一旦拆分后某个集群出现异常，可以快速切回原路径，避免影响业务。
  8. 补齐监控和隔离治: 拆分完成后，要把各小集群的流量、资源、异常率、限流熔断等指标独立监控起来，这样隔离才真正可观测、可治理

好处

1. 提高系统的可用性和容错性值
    1.1 避免个别应用的问题影响到全局的, 进行了故障隔离, 
2. 提升了可维护性
    2.1 针对指定功能的使用上,
3. 成本上的控制
    低频的请求可以部署在配置较低的机器上去

针对大的请求需要怎么处理?

1. 会限制单个请求的大小, 每个请求的大小限制在64M, 同时针对大文件请求有专门的集群去处理。
2. 返回数据的时候会开启gzip 压缩。 频繁压缩会吃CPU

1. 将耗时长的应用和核心交易应用的集群分开, 防止耗时长的应用占用过多的TCP 连接
2. 由于做了全异步处理, 耗时长的应用只会占用过多的端口号
3. 监控上去处理, 针对耗时长的是否合理, 对于不合理的请求直接限流
4. 自身保护机制上和后端单台机器限制1000个TCP 连接, 整个应用限制在5000 个连接。

注册中心为什么要用ZK

我们当时选择 ZK，而不是 Eureka，核心原因是网关作为核心流量入口，对服务实例列表、路由配置、权重和规则变更的正确性要求比较高。如果注册中心在实例上下线、配置变更或者节点异常时出现较长时间的不一致，网关就可能把请求转发到错误实例，这对金融场景风险比较大。从 CAP 的取向上看，ZK 更偏 CP，能够更好保证数据的一致性；而 Eureka 更偏 AP，可能会在一段时间内数据不一致。对我们来说，这里的取舍是接受一定的可用性损失，换服务注册数据和配置视图的一致性，从而降低错误路由、错误转发和规则失效带来的风险。
而是因为网关依赖的注册发现和配置元数据对一致性要求更高，因此我们在这个场景下更倾向选择 ZK

全链路灰度

根据请求过来header 的标签, 如果带上了gray 标签, 则将流量转发到灰度分组中去, 同时给下游转发的时候, 也在header 中记录上对应的标签
全链路灰度的核心是灰度标签的透传, 请求进入网关后, 先根据header 识别灰度流量, 并把它转发到对应的灰度分组; 在继续调用下游的时候, 再把灰度标签进行透传下去, 让下游也按照灰度标识选择对应的实例.

网关自身的灰度特性, 灰度机器的配置下发

网关作为流量入口，一旦用户配置错误，会直接影响全量流量，故障影响面很大。为此我们设计了网关配置灰度发布机制，将配置出错引发的故障率降低 70%。
方案是在网关集群中独立部署灰度节点，将1% 的线上流量路由到灰度机器。用户变更网关配置后，先发布到灰度节点进行验证，通过观测灰度节点的流量、响应、错误指标，确认配置生效且行为符合预期；验证无误后，再把配置全量同步到生产网关集群。一旦灰度验证发现异常，可以快速回滚灰度配置，错误只会影响这 1% 流量，避免错误配置直接全量上线引发大面积故障

各个组成部分

QConfig 整体分为 Portal、Server 和 Client 三层。Portal 负责配置变更入口，Server 负责变更分发和客户端连接管理，Client 负责版本感知和配置拉取。配置发布时，Portal 会先把变更持
久化到数据库，再把配置文件名、环境、版本号这些元信息广播给各个 Server。Server 根据本地维护的订阅关系，找到对应客户端，并通过长轮询通知客户端有新版本；客户端再根据最新版本号
主动拉取配置内容并更新本地缓存。

配置的发布流程

配置发布的完整链路，我一般会按 Portal、Server、Client 三段来看。
第一步，用户在 Portal 提交配置变更，最新配置内容持久化到数据库，同时生成新的版本号。
第二步，Portal 把这次变更的元信息广播给各个 Server，元信息通常包括配置文件名、环境和版本号。
第三步，Server 收到变更通知后，会根据自己内存里维护的订阅关系，找到哪些客户端正在监听这个配置。
第四步，客户端和 Server 之间是长轮询关系，客户端会持续挂一个监听请求在 Server 上。Server 发现对应配置有新版本后，就把最新版本号返回给客户端。
第五步，客户端感知到版本变化后，再主动向 Server 拉取最新配置内容，并更新本地缓存，完成配置生效。

为什么是长轮询 + 客户端主动拉取，而不是 MQ 或服务端直推

我们当时选择“长轮询 + 客户端主动拉取”，核心考虑有两个。

第二是实现和运维复杂度更可控。长轮询本质上是基于 HTTP 的通用模型，各种语言都容易接入

所以最终我们选择长轮询 + 客户端主动拉取，不是单纯因为实现简单，而是因为它在系统复杂度和链路可控性之间是一个更合适的平衡。

机房故障恢复时，客户端怎么重新收敛到同机房

客户端和服务端之间不是固定写死连接的，而是会定时拉取一份可用服务节点列表。这个列表里除了 IP 信息，还会带上节点所属机房的 IDC 标识。客户端本身也知道自己所在的机房，所以每次刷新节点列表时，都会优先选择和自己同 IDC 的服务节点。

在机房故障期间，如果本机房节点不可用，客户端会先切到其他机房的可用节点，保证配置读取和推送链路不中断。等本机房恢复之后，客户端下一轮刷新可用节点列表时，就能重新感知到同机房节点已经恢复，再根据 IDC 信息优先收敛回本机房。

服务端节点之间的可用状态感知，底层是通过 Eureka 做注册和心跳维护的。也就是说，客户端看到的可用节点列表，其实是服务端基于 Eureka 注册信息整理后返回的。

另一方面客户端集中拉取又会导致缓存击穿，大量请求回源到数据库。

针对这个问题，我主要做了两件事。
第一，把原来的逐条保存、逐条通知改成批量保存和批量通知，降低数据库写压力。
第二，在读取链路上增加预热机制，在通知前后提前把热点配置加载到缓存，避免客户端集中拉取时击穿缓存、直接回源数据库。

young gc 从2秒到10ms

直接:
当时服务端 GC 停顿已经明显影响到配置推送和系统稳定性，高峰时最长能到 2 秒。我先在 G1 上做了一轮调优，验证能不能靠低成本方式解决，结果虽然有改善，但离目标还有明显差距。最终我判断这是收集器能力边界问题，所以推动切到 ZGC，最后把 GC 停顿从 2 秒级压到了 10ms 级，系统抖动明显收敛。

详细:
当时我们遇到的核心问题是服务端 GC 停顿比较明显，Young GC 最长能到 2 秒左右, 常态下单次停顿大概在 几百毫秒 ，对配置推送时效和整体稳定性影响很大。我的排查思路不是直接换收集器，而是先判断这是不是可以通过 G1参数调优解决。

第一步，我先看了新生代占比和停顿目标。当时新生代比例比较小，我先尝试调大 G1NewSizePercent，同时把 MaxGCPauseMillis 从默认值进行了调整，希望通过扩大新生代、降低回收频率来减少抖动。

调完之后，Young GC 的频率和停顿时间都有一定改善，说明参数优化是有效的，但整体效果仍然没有达到我们的预期目标。基于这个结果，我判断问题已经不是简单的参数配置问题，而是 G1 在当
前对象分配和内存回收模型下，对低停顿目标的支撑有限。于是最后我推动把收集器从 G1 切换到 ZGC。切换之后，GC 停顿时间从原来的 2 秒级下降到了 10ms。

这个问题我一开始没有直接换 ZGC，而是先在 G1 上做参数调优，比如调大新生代比例、调整 MaxGCPauseMillis，希望先验证是不是参数问题。调完以后，Young GC 频率从 70 多次降到了 30 多次，但单次停顿反而从 300ms 上升到了 450ms 左右，总体耗时改善不明显。基于这个现象，我判断问题不是简单调参能解决的，而是 G1 在当前场景下已经接近瓶颈，所以最后切换到了 ZGC，最终把 GC 停顿从 2 秒级压到了 10ms 级

核心和非核心的逻辑隔离

这块我主要做了两层隔离。第一层是数据层隔离，把配置文件本身的数据和配置操作日志分库处理。这样即使日志写入失败，也不会影响配置数据的更新和发布，保证核心配置链路优先可用。

第二层是执行资源隔离。针对 Portal 的关键入口，尤其是 RestAPI 请求，我把处理逻辑异步化，放到线程池里执行，同时按用户类型做资源分级，比如 DBA 和普通用户使用不同的线程资源配额，核心用户会有更高保障，避免普通流量把关键配置变更能力挤占掉。

整体上，这套设计的目标就是让核心链路和非核心链路解耦，在异常场景下优先保证配置变更主流程可用。

测试时间降低

当时测试耗时长，核心原因是原来的单元测试更多是按功能点串行验证，场景覆盖虽然有，但执行模型比较重，没法快速模拟真实用户在配置变更、监听、拉取这些链路上的并发行为。

我后面做的优化，主要是在单元测试整体架构上改了两点。第一，是从用户视角去构造测试场景，不再只是验证单个方法或者单个接口，而是把配置变更、服务端通知、客户端拉取这些关键链路串起来做端到端模拟。第二，是把原来很多串行执行的测试过程改成并行处理，让不同配置类型、不同变更场景、不同监听和拉取动作可以并发执行，更接近真实线上场景。

这样改完之后，一方面测试覆盖更贴近真实业务，另一方面执行效率也大幅提升，所以整体测试时间从原来的分钟级压缩到了秒级。

全链路埋点

这块全链路埋点的核心设计，其实就是给一次配置变更生成一个全局唯一的 TransactionId，然后把它贯穿 Portal、Server 和 Client 三段链路。

具体来说，用户在 Portal 通过 RestAPI 发起配置变更时，系统会先生成一个 TransactionId，并把这个 ID 绑定到本次变更请求上。请求发送到 Server 时，会把这个 TransactionId 一起透传过去，服务端在处理变更、通知客户端、记录关键日志时，也都会带上同一个 ID。客户端收到版本变更通知后，后续的拉取和处理日志同样继续携带这个 TransactionId。

这样一来，一次配置变更从 Portal 发起、Server 接收处理，到 Client 感知和生效，整条链路上的关键日志都能通过同一个 TransactionId 串起来。

配置中心整体高可用怎么保证

配置中心的高可用，我一般分成 Portal、Server、机房、存储和 Client 五层来看。

第一，Portal 挂了，不影响客户端读取配置。因为 Portal 主要负责配置管理和发布入口，客户端读取走的是 Server 链路，所以最多影响配置变更，不影响已发布配置的读取。
第二，单台 Server 挂了，客户端可以通过注册发现拿到其他可用节点并自动切换，所以不会影响配置读取。
第三，单个 IDC 故障时，客户端会降级访问其他机房的可用节点，等本机房恢复后再重新收敛回同机房，这样可以保证跨机房容灾。
第四，如果 MySQL 异常，系统也不会立刻不可用。因为客户端本身会保留已经生效的配置，本地内存和本地缓存都还能继续兜底；如果你们服务端也做了磁盘缓存，也可以一起讲成服务端和客户端
双层缓存兜底。
第五，如果所有 IDC 都不可用，客户端仍然可以使用本地缓存中的最后一个可用版本，保证业务读取不至于中断。
所以整体上，它的高可用核心是：Portal 和读取链路解耦、多节点自动切换、跨机房容灾，以及客户端本地缓存兜底。

批量通知如何保证幂等、一致性和不丢失

这块我一般分成发布侧和消费侧两层来看。

发布侧主要解决并发变更一致性问题。我们的版本号是单调递增的，每次配置变更都会生成新版本。用户通过 RestAPI 发起变更时，会带上自己认知的当前版本号，服务端落库时基于版本号做乐观锁校验。如果请求里的版本号和数据库当前最新版本不一致，说明中间已经有别人改过了，这次更新会直接失败，避免并发覆盖。

消费侧主要解决通知幂等和最终一致问题。批量通知本身允许重复，也允许短暂乱序，但客户端只认版本号。客户端本地会保存每个配置的最新版本，只有收到更高版本时才会拉取最新配置；如果是重复通知或者旧通知，就直接忽略，这样就保证了通知处理的幂等。

至于不丢失，我们不会把单条通知当成唯一依据，而是把版本号作为最终真相源。即使某次通知没收到，客户端后续通过下一轮长轮询或者定时拉取，发现本地版本落后，还是会把最新版本补回来。所以整体上，我们是通过乐观锁保证写入一致，用版本号保证通知幂等，再通过客户端主动拉取实现最终一致。

GC 算法

1. CMS
    1. 初始标记
        从GCRoots 出发的直接可达性对象, 需要进行STW, 
    2. 并发标记
        在初始标记的基础上, 标记处内存中所有的可达性对象, 此时没有进行STW, 用户线程和GC 线程同时在运行.
    3. 重新标记	
        需要进行STW, 对并发标记遗漏的对象进行修正, 在并发标记起期间产生的不可达对象需要在下一次GC 周期才能被回收
    4. 并发清除
        清除所有未被标记的对象, 进行对象回收, GC 线程和 用户线程同时在运行
    缺点: 
        1. 碎片化验证, 清除过程中不对内存进行压缩整理, 导致内存碎片话严重
        1.1 影响: 碎片化严重, 可能会导致老年代无法分配达对象, 触发full GC
        2. 浮动垃圾: 在并发标记期间产生的垃圾, 无法在当前GC周期被清除, 只能等到下一次GC
        2.1 影响: GC 效果不如预期, 需要预留更多的内存空间
        3. 某些情况下会退化成单线程回收
        3.1 如果堆内存不足以支撑程序的内存分配, 进而出发一次Full GC
        3.2 年轻代向老年代晋升, 如果老年代没有足够的空间去容纳这些对象的时候, 也会导致CMS 失败, 从而退化成单线程的Serial Old 收集器
        3.3 空间碎片化, 由于CMS 回收产生的碎片化, 导致大对象无法找到连续的内存进行分配, 最终触发full GC
2. G1
    其中-XX:G1NewSizePercent  新生代比列默认时5%
    使用标记-整理算法
        1. 标记阶段
            1. 初始标记
            从GC Roots 出发, 标记直接可达的对象, 需要进行STW
            2. 并发标记
                从GCRoots 出发, 找出存活对象, 应用线程和GC线程是可以同时活动的, 
            3. 再标记
                标记在并发标记时转移的对象
        2. 清理阶段
                清点出有存活的对象和没有存活的对象
        3. 复制阶段
            重新分配对象内存和复制成员变量, 转移的时候需要进行STW, 复制的耗时和存活对象的数量以及对象的复杂程度成正比
          
        **初始标记**
            标记从GC Roots 出发的可达对象 需要进行STW
        - **并发标记**
            标记整个堆中的存活对象, 不会进行STW
        - **最终标记**
            完成并发标记, 并且处理在并发标记期间导致应用对象的变化, 需要进行STW
        - **筛选回收**
            确定进行回收, 并根据收集的数据区域进行回收
        - **拷贝回收**
            将存活的对象从回收区拷贝到新的区块, 方便进行回收
            特点:
                region 管理, 每个区域可能是Eden 区, 也可能是Survivor区, 也可能是old区
                并发标记和整理, 支持并发标记, 降低了STW 
                可预测的停顿时间
                优先回收: 维护一个优先队列, 根据各个区域回收的价值(回收成本和收益) 决定哪些要优先回收
            G1 怎么解决浮动垃圾:
                将对分割成多个region, 更加灵活的去管理和回收内存, 降低浮动垃圾的影响
                垃圾回收的时候, 可以进行并发标记和整理, 最大限度的降低程序的停顿
3. ZGC
    通过染色指针和读屏障技术解决了对象转移的问题, 从而降低了耗时
    染色指针: 指针中存放了对象的一些信息, 例如对象是否被标记, 是否移动了, 相当于用空间换时间

MGR 原理

1. 基于 Paxos 分布式一致性协议和自动化故障恢复机制, 允许多个Mysql 服务器组成一个复制组, 实现高可用性和容错能力
1.1 分布式协议基于 paxos 协议
1.2 所有写操作都是需要经过所有组员的一致同意, 写操作先在主节点上提交, 主节点会通过 GTID (全局事物ID) 将事物广播给其他节点, 只有多数节点同意了, 事物才是被认为可执行的
1.2.1 冲突检测机制, 确保全局唯一
    基于writeSet 的冲突检测机制: 每个事物提交的时候, MGR 会生成一个write-set, 记录了该事物中所有的修改, 相当于对该事物的写操作生成了一个集合
                    冲突检测: 当一个节点尝试提交事物的时候, 会将该事物的write-set 与组内其他节点已提交但未应用的事物write-set 进行比较, 判断是否有冲突发生

1. 不过 G1 为了解决 CMS 并发清理导致内存碎片化的问题，使用了复制算法转移对象，这样如果在转移过程中 GC 线程和用户线程并行，会导致指针无法准确定位对象的问题

染色指针: 每个对象的指针在存储时都包含了附加的信息，用于表示对象的状态，比如是否是可达对象、是否需要被回收等
读屏障: 在 ZGC 中，读屏障用于捕获并记录正在被并发标记的对象引用，以便在后续的并发标记阶段中正确地标记这些对象。读屏障能够保证并发标记的准确性，防止对象在标记过程中被移动或修改引用关系导致的错误标记。

有此酒店有个用户反馈过来说配置变更后推送没有推送成果, 需要进程重启后再去拉取配置文件. 并且出现的概率的话, 大概是在半年前出现过一次, 现在改了一个配置, 几百台机器里面有一台配置是没有拉取到.
这个问题难排查主要有三个原因：第一，请求链路看起来像是中间“丢了”，线程状态和预期不一致；第二，现有日志无法完整反映请求实际执行过程；第三，问题只在 OOM 这种低概率异常场景下出现，本地很难直接复现。

我的排查思路分成两步。第一步是基于现场做静态分析，我先把用户当时的内存文件 dump 下来，再通过 MAT 分析线程和堆里的，确认请求到底卡在哪一层。第二步是做浮现复现，我把 Netty 发送请求的逻辑单独封装出来，在本地持续加压，并主动触发 System.gc() 去触发OOM 场景，压测了3天最有，最终复现出来。复现之后，我根据补充的关键日志，发现这个是netty3.x 里面在 oom 的时候对超时设置有个bug, 导致超时没有生效, 同时线程丢失了. 没有日志因为发生了ooM, 抛出异常, 自身异常没有catch 住。最后将netty的版本进行升级进行了解决。

比较难熬的时间点 / 你是怎么扛过来的？

我印象里比较难熬的一次，是在汇付做网关时处理一个北京大客户支付超时的问题。
因为这是大客户问题，影响的是交易体验和客户信任，而且最开始用户侧报超时，但网关侧没有任何日志，短时间内很难直接解释清楚原因，所以当时压力会比较大。

我当时没有陷在情绪里反复看日志，而是先把问题拆层。第一步先确认应用层有没有收到请求，所以我在网关侧针对商户 ID 增加专项日志；第二步和客户一起做小额联调，看能不能复现；第三步当问题再次出现但网关仍然无日志时，我就把重点从代码层切到了接入链路和网络层；第四步拉着阿里云一起排查，从 SLB 到网关入口逐层确认，最后定位到跨地域网络抖动。

定位清楚以后，我们没有只做临时止血，而是在北京专门部署一套 SLB 和网关入口，让客户流量就近接入，再通过内网专线和上海侧系统打通，减少跨地域公网链路的不确定性。
我觉得我扛压力的方式，不是硬顶，而是把复杂问题一层层拆开，让范围持续收敛。只要问题在不断缩小，其实压力就会慢慢变成推进力。

你怎么看待加班 / 压力？

我能接受阶段性的高强度投入，尤其是核心项目上线、故障处理、关键阶段交付这些场景，本身也需要有人扛住。
但我理解更重要的不是长期靠加班解决问题，而是通过更好的架构设计、流程、规范和治理，把很多问题提前消化掉。
对我来说，压力本身不是问题，关键是这个投入有没有价值，能不能真正解决问题。

你和别人意见不一致时怎么办？

如果和别人有分歧，我一般会先回到目标本身，看我们分歧的是技术方案，还是对问题定义就不一样。
如果是方案分歧，我会把关键 trade-off 摆出来，比如性能、风险、成本，然后尽量用数据、线上案例或者小范围验证去支撑判断。
我不太倾向于纯靠经验拍板，尤其是在核心系统上，最好还是让事实和结果说话。
当然，如果最后已经形成一致决策，我也会尊重团队结论，把事情先往前推进。

你带人 / 协作时更看重什么？

如果是带人或者协作，我比较看重三件事。
第一是边界清晰，谁负责什么要明确；
第二是质量前置，方案、代码 review、测试、灰度这些环节要尽量往前做；
第三是结果闭环，不只是开发完成，而是上线效果、监控指标、故障预案都有人跟。
我比较希望团队不是把活做完，而是把系统做稳。

任务怎么分配

我分配任务时，通常会先把需求拆成几个部分：核心链路 或者是 相对独立的功能点。核心链路，我一般会自己先兜住，或者分给经验更匹配的人；边界清晰、依赖少的部分，会分给实习生或者外包同学去做。

在分配时我会比较看三件事：
第一是任务本身的风险和复杂度，
第二是成员当前的能力和熟悉度，
第三是依赖关系和排期。
我的目标不是平均分任务，而是让关键路径可控，同时让每个人都能在自己能承担的范围内发挥作用

如何进行code review

我做 code review 会优先看几个层次。
第一是业务和逻辑是否正确，边界条件有没有覆盖；
第二是稳定性风险，比如并发、超时、异常兜底、是否可能影响线上；
第三是可观测性，比如关键日志、监控埋点、
最后才是代码结构和可读性。
我不太会把 review 只做成格式检查，更关注这段代码上线后会不会出问题、出了问题能不能发现、发现后能不能定位

团队成员进度落后怎么处理

我一般不会先把问题归因到人，而是先判断进度落后的原因。
通常会先看是方案理解不一致，还是执行上确实有困难。原因不同，处理方式也不同。
如果是任务拆得太大，我会帮他把任务再拆细；
如果是技术难点卡住，我会一起过方案或者直接一起实现；
如果是优先级和节奏有问题，我会重新对齐目标和时间点。
我的核心思路是尽快暴露风险、尽快调整，而不是等到最后才发现进度已经失控。

如果我们没录用你，你觉得可能是什么原因？

如果没有录用，我会理解可能有两种原因。
一种是岗位希望的人选在某些技术方向上和当前需求更直接匹配；
另一种也可能是我在表达上没有把自己的经验和岗位需求对应得足够清楚。
但从我的经历来看，我在网关、配置中心、稳定性和核心链路治理这些方面确实是有积累的，所以如果是匹配问题，我会尊重结果；如果是表达问题，我也会复盘自己后续怎么讲得更清楚。

还有什么想问我们的？

可以反问以下问题：

  • 您怎么看这个岗位上表现比较好的同学？通常他们最突出的特质或者能力是什么？
  • 如果我加入这个岗位，您觉得前期最可能遇到的挑战是什么
  • 如果我有机会加入，您会希望我在前 3 个月优先解决哪些问题，或者做到什么程度？
  • 网关、配置中心、稳定性平台这些能力目前建设到什么阶段？
  • 这个岗位对技术 Owner 的预期，更偏方案设计，还是偏团队带动和落地推进？
  • 团队现在最希望新加入的人，在前 3 到 6 个月解决什么问题？

回答统一公式

综合类问题回答时，尽量套这个公式：

先表态，再解释原因，最后落到自己的做法。

例如：

  • 缺点：我以前偏谨慎，因为核心系统风险高，现在通过灰度和分层判断来平衡。
  • 为什么换工作：想继续做基础架构，因为这和我的积累最匹配，希望承担更强 Owner 职责。
