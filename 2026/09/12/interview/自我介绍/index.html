并行聚合是怎么做的:

====

并行聚合的实现上，核心分成五步。

第一步是任务拆分。入口请求进来之后，我们会先根据区域配置、广告源配置以及请求上下文，解析出当前请求需要调用哪些三方广告源，然后把它拆成多个相互独立、没有前后依赖关系的子任务。

第二步是并行执行。因为这些子任务之间没有依赖，所以不会再像以前一样串行调用，而是直接并发发起请求。这样整体 RT 理论上就会从“多个下游耗时累加”收敛到“最慢一路下游的耗时”。

第三步是资源隔离。这里我没有把所有任务放到同一个线程池，而是按 A/B/C 三类特性拆到不同线程池中处理。因为不同广告源的耗时和流量特征差异很大，如果共用一个线程池，一旦某一路慢请求变多，就会把其他正常流量拖垮。所以拆线程池本质上是在做隔离。

第四步是并发控制和超时治理。在线程池隔离之外，我又针对每类广告源加了 Semaphore 并发配额控制，限制对下游的最大并发，超过阈值就直接降级，避免请求堆积。同时针对不同广告源配置差异化超时时间，任一路超时后直接结束，不阻塞其他并行任务。

第五步是结果聚合。等各路任务返回后，聚合层会把成功返回的素材结果统一组装。如果某一路失败或者超时，不会让整个请求直接失败，而是尽量保留其他成功结果返回给客户端，避免局部故障放大成整体无结果。

3. 为什么还要做三个线程池？

这里其实是这个项目比较重要的一个架构点。
我们并不是简单地把所有三方请求全部扔到一个线程池里。
因为不同三方的特点不一样。
比如：

  • A 类：高频、RT 比较短、主要追求吞吐
  • B 类：中等耗时
  • C 类：RT 比较长，而且长尾比较明显
    如果全部使用一个线程池，那么 C 类三方出现大量慢请求的时候，就可能把线程池里的资源全部占满。
    最终导致：

    一个慢三方把其他正常三方也拖慢。
    所以我们按照三方来源的特性，把它们划分成了 A/B/C 三类线程池进行隔离。
    这样即使 C 类三方出现大量慢请求，也不会直接把 A、B 两类请求的线程资源全部占用。

4. 线程池参数怎么设计？

这里我建议你面试的时候重点讲 Little’s Law，这个会让你的回答从“我调了几个参数”提升到“我有容量模型”。
我们的峰值场景大概按照单 Pod 4500~4600 QPS 来进行容量设计。
同时根据实际压测和监控，我们发现真正占用线程池资源的平均时间并不是完整的下游 RT，而是线程池任务在发送请求以及处理相关逻辑上的平均资源占用时间，大概按照 10ms，也就是 0.01s 来进行线程资源估算。
这里使用 Little’s Law：

并发数 ≈ QPS × 平均资源占用时间
比如按照 4500 QPS：
4500 × 0.01 = 45
也就是说理论上的平均并发资源占用大约是 45。
然后我们再根据实际流量、不同来源的流量占比以及安全冗余系数进行容量放大，最终确定三个线程池的 core/max、队列以及 Semaphore 参数。

6. 为什么还需要 Semaphore？

这个地方你面试的时候可以重点说。
线程池解决的是线程资源隔离问题，Semaphore解决的是下游请求并发数控制问题。
比如 C 类三方平均 RT 比较高，而且长尾明显。
如果单纯依赖线程池，在流量突然升高或者三方 RT 突然变长的时候，可能会出现大量请求堆积。
所以我们又在三方调用层增加了 Semaphore。
例如：

通过 Semaphore 控制同时发送到某一类三方的请求数量。
超过并发阈值之后直接拒绝或者快速降级，而不是无限制地把请求压给三方。
这样能够避免：

流量突增 → 请求堆积 → 线程池耗尽 → GC增加 → RT升高 → 服务雪崩
形成这种级联问题。

7. 超时和降级

另外我们对不同类型的三方设置了不同的 timeout。
因为 A/B/C 的 RT 特征不同，所以不能统一设置一个超时时间。
例如：

  • A：150ms
  • B：500ms
  • C：800ms
    如果某个三方超过 timeout，就直接进行降级。
    也就是说：

    一个三方失败，不影响其他三方正常返回。
    最后聚合层只把已经成功返回的广告素材进行统一聚合。

异步IO 是怎么做的:

我们这个广告聚合服务入口 QPS 约 900，并行调用多方广告源之后，下游总 QPS 会放大到 4600。改造前使用同步 HTTP Client，业务线程在等待三方网络响应时会阻塞。一旦下游 RT 抖动，大量业务线程卡在 IO 等待，线程池资源很容易耗尽，引发服务稳定性问题。

====所以我将同步客户端改造成基于 Netty 的异步非阻塞 IO 模型。业务线程只负责发起任务，网络读写交给 Netty EventLoop 处理，通过回调接收结果，实现计算线程和网络 IO 的隔离，少量线程就可以支撑大量并发请求。
但异步模型会带来新风险：请求发送速度变快，如果没有约束，会造成 Socket 连接数暴涨，直接压垮下游三方。因此我们在异步调用链路增加 Semaphore 做单机维度的下游并发配额控制。针对每个广告源独立限制最大并发，超过阈值直接快速失败并触发降级，避免流量失控引发级联故障。

问：异步 IO + Semaphore，和前面多线程池隔离方案是什么关系？
答：线程池是隔离本机内不同广告源的业务任务线程，解决内部资源争抢；异步 IO 释放线程，提升单机吞吐；Semaphore 是管控对外下游的并发请求量。三者配合：线程池隔离内部资源，异步 IO 提升线程利用率，Semaphore 保护下游依赖，多层防护。

问：异步回调有什么坑，怎么处理？
答：主要风险是回调异常、超时不触发带来内存泄漏。我们给所有异步请求统一设置超时，增加回调埋点监控成功、超时、异常指标，同时每个下游使用独立连接池，防止单个三方故障污染全局连接资源。

Sempahore 实现原理

通过AQS 去进行实现, Semaphore 内部有一个共享的 state,表示剩余的 permit 数量。acquire 的时候通过 CAS 尝试把 state 减一,减成功就拿到许可;减不了就阻塞等待(或快速失败),等待的线程会被放进 AQS 的队列里;release 时把 state 加一,唤醒等待队列里的线程。因为高并发下可能有很多线程同时来竞争 permit,所以必须用 CAS 保证修改 state 的原子性,避免并发安全问题, 在进行tryAcquire 的时候去进行处理。

Sempahore 分类

线程池按照三类任务特征分成 A/B/C 三类,用三个线程池做资源隔离是合理的。但 Semaphore 更应该细化到每一个具体三方,比如五个三方就各自有独立的并发控制器,防止某个三方流量突增把同一线程池里的其他三方也拖垮。

GC 优化怎么做的:

===并行改造后下游等待时间降了，但 Young GC 最高到 2 秒。先排查内存泄漏，Old 区稳定排除年代问题，判断是 Young 区短对象过多。用 Arthas Profiler 定位，热点在三方数据序列化反序列化，还有每次克隆广告曝光模板 —— 并行后每次任务都克隆，产生大量临时对象。优化时把模板改成只读，去掉克隆，每个请求只传必要上下文，任务完成后统一填充模板，减少 90% 以上中间对象，最终 Young GC 降到 10 毫秒。

并行化改造之后，整体下游等待时间虽然降下来了，但我们观察到 Young GC 的 Pause 最高到了 2 秒。这个时候我先没有急着去调 JVM 参数，而是先判断问题性质。

第一步先排除内存泄漏，因为当时 Old 区整体比较稳定，没有明显持续上涨，所以判断主要压力不在老年代，而是在Young 区对象分配过快、回收压力过大。

第二步我用 Arthas 的 profiler 去看 allocation flame graph，发现热点主要集中在SerializationUtils.clone，以及 JSON 反序列化之后的一些对象装配和 copy 操作。结合链路分析后发现，问题本质上是并行化之后，多路结果会在同一时间窗口内同时存在，导致请求过程中的临时对象分配量明显增加，从而把Young GC 压力放大了。

所以这个问题我没有选择简单去调大堆或者只改 GC 参数，因为那只能延后问题，不是从根因上解决。我的处理方式是从对象生命周期和数据结构设计上入手：把模板改成只读，去掉 clone；在创建任务时只传必要的 contextHolder；等所有任务执行结束后，再统一对模板数据做填充。这样一次请求内只保留一份骨架数据和一份下游结果引用，避免了大量中间对象 copy。

改完之后，Young GC Pause 从 2 秒左右降到了 200 毫秒左右。对我来说，这次优化的重点不是 JVM 参数调优本身，而是通过分配热点分析，把问题定位到对象模型和装配方式上，再从代码结构层面把分配速率降下来

基于配置监听的变更感知手段是怎么做的

我们原来是 Spring Boot 定时任务每 5 分钟轮询数据库,实时性较差。后来改成“事件通知+ 主动拉取+ 定时轮询兜底”的方案。运营修改素材配置时先落库,然后更新配置中心的版本文件。服务端监听到变更事件后,再主动拉取数据库的最新配置写入本地。同时保留原有 5 分钟的定时任务作为兜底,以防事件丢失。这样正常情况下可以做到近似秒级感知配置变化,同时又不完全依赖事件机制,可靠性也有保证。你可以强调这不是简单把 5 分钟轮询改成“推送”,而是把原来的 pull 模式升级为“事件驱动 push 加数据库拉取 加 定时轮询兜底”的混合模型。这样既提升了实时性又保证了最终一致性和可靠性。

分级熔断与缓存处理是怎么做的:

我们当时做分级熔断和缓存兜底，核心目标是两点：第一，在下游部分异常时尽量保住广告返回结果和收益；第二，避免下游故障直接放大成整体链路不可用。

具体实现上，我们会基于滑动窗口去持续评估每个下游广告源的健康状态。以 10 秒为一个统计窗口，窗口内记录请求总数、成功数和失败数，并用失败次数 / 总请求数计算当前失败率。基于这个失败率，我们把下游健康状态分成 4 个 等级。

L0 是正常状态，也就是失败率低于 20%。这个阶段说明下游整体稳定，请求正常转发，不做额外干预。

L1 是轻微异常，失败率在 20% 到 50% 之间。这个阶段我们认为下游开始有波动，但还没有严重影响整体可用性，所以请求仍然正常转发。同时把成功返回的内容写入 Redis，作为后续进一步异常时的兜底数据。缓存维度会按providerId + 国家 + 语言 + 品牌 组合，尽量保证命中结果和用户请求场景匹配。

L2 是中度异常，失败率在 50% 到 80% 之间。这个阶段我们仍然会尝试正常请求下游，但如果调用失败，就不再直接把失败暴露给上层，而是优先读取 Redis 缓存做兜底。如果缓存有数据就返回缓存，没有缓存就直接返回空结果或者进入上层降级逻辑。这样可以在下游不稳定时尽量保住返回结果。

L3 是严重异常，也就是失败率超过 80%。这时我们认为下游已经接近不可用，继续大量转发只会放大故障，所以会进入强熔断状态，正常流量不再直接打到下游，而是优先读取缓存返回。同时为了避免永久熔断，我们会开启探针恢复机制，比如每秒放 5 个探针请求去检测下游是否恢复。当探针结果连续恢复正常后，不会一下子把全部流量切回去，而是按 5%、20%、50%、80%、100% 这样的节奏逐步放量，避免下游刚恢复时再次被流量冲垮。

所以这套机制本质上不是简单的“失败就熔断”，而是通过滑动窗口做健康评估，再结合不同故障等级选择不同的处理策略：轻微异常时做缓存预热，中度异常时失败读缓存，严重异常时强熔断加探针恢复。这样既能控制故障扩散，也能尽量保住广告曝光和收益

方案的取舍

这个方案最大的取舍，是牺牲一部分实时性和实现复杂度，换下游异常场景下的整体可用性和收益稳定性。比如进入中重度异常后，我们允许一部分请求直接走缓存，这样返回内容可能不是绝对最新的，但能尽量保住曝光和填充，不至于因为三方故障导致整体无结果。另一方面，分级熔断、探针恢复、渐进放量这些机制也会增加系统复杂度，但它的价值是能把故障控制得更细，不会出现要么全量打下游、要么一刀切全熔断的情况。
所以本质上，这个方案是在收益链路里用一定的实时性损失和系统复杂度，换更强的故障收敛能力和整体稳定性

追问 1：为什么选用 10 秒滑动窗口，不是更长或者更短？

答：窗口大小是权衡灵敏度和抗抖动。窗口太短，少量突增失败就会误判熔断；窗口太长，无法快速感知下游故障。10 秒窗口既能平滑瞬时毛刺，又可以较快捕捉下游持续恶化的故障，适配我们广告素材调用的 RT 特征。

追问 2：滑动窗口是怎么实现的？是环形桶滑动窗口吗？

答：采用分桶滑动窗口，把 10 秒拆成多个时间桶，每个桶独立统计成功、失败计数。时间滑动时淘汰过期桶数据，只保留最近 10 秒的统计，避免单个大窗口内存开销，同时保证统计的时效性。

追问 3：阶梯恢复为什么是这几个比例？

答：阶梯式放量是为了渐进验证下游恢复能力。从小流量 5% 开始观察下游指标，确认稳定后再提升流量比例，一旦在某个阶段失败率再次升高，立刻停止放量并回退到缓存模式，防止故障反复。

追问 4：失败率计算的时候，有没有考虑请求量太少的场景（低基数误判）？

答：这里有个保护机制，如果窗口内总请求量低于最小阈值，不参与失败率计算，防止少量请求的随机失败，误触发降级，这是防止熔断误触发的保护逻辑。

网关的整体架构是什么样的

我们这个网关整体上可以分成三层：控制面、配置存储与分发层，以及数据面

控制面主要是控制台，负责路由、限流、鉴权、权重等规则配置，同时也承接外部系统的一些配置推送。配置变更后会先持久化到数据库，再通过 ZooKeeper 做配置通知和动态分发。网关服务节点作为数据面，会监听 ZooKeeper 上的配置变化，并刷新本地配置缓存。这些配置既包括路由规则，也包括后端实例列表、权重分组、限流规则等运行时数据。

在请求链路上，外部请求会先经过 WAF 和 SLB，再进入网关。网关收到请求后，会先根据 Host 和 Path 做路由匹配，确定目标应用，然后再结合应用对应的实例列表、权重和分组规则，选择具体的后端实例进行转发。在这个过程中，网关还会做鉴权、限流、签名校验等通用治理逻辑。

和偏通用型的网关相比，我们这个网关会更贴近业务场景。除了常规的路由和转发能力外，还会解析请求体里的业务字段来做验签和更细粒度的限流。比如公司内部很多场景会约定商户 ID 放在 Body 第一层，所以我们支持基于这个字段做流量治理。但这里也有明确取舍，我们没有支持任意层级的嵌套解析，因为那样会明显增加解析开销、规则复杂度和维护成本，所以只支持约定格式下的有限解析能力

tomcat 换成netty

当时压测和线上高峰期观测，通过 vmstat 监控发现，流量上涨后 CPU 负载飙升，接口 RT 显著恶化。

在请求量大的情况下：

1. CPU 负载发现急剧上升
2. 整体请求的耗时一下子上来了

排查原因：

vmstat 用于观测整机 CPU、内存、上下文切换等系统指标，核心看 cs 上下文切换、us/sy CPU、r 就绪队列。
我当时用 `vmstat 1`，每秒采集一次数据。在流量上涨时，观测到 cs 暴涨、sy 升高，判断是大量线程带来频繁上下文切换。后续搭配 pidstat，定位到是 Tomcat 进程产生大量线程切换开销。

1. 由于线程开的太多了，上下文切换比较频繁
2. 有一些请求会由于 tomcat 阻塞住了，导致外部请求有堆积。将允许的线程数开大的话，会导致线程切换更加频繁

解决办法：将网络框架换成 netty 去处理。

1. tomcat 相比较于 netty 的线程模型

   tomcat 采用的是多线程阻塞模式，每个请求对应到一个线程上去。在请求量变多的情况下，会导致线程数急剧上涨，从而带来线程上下文的开销；同时线程池中的核心线程数到了上限后，后面过来的请求就需要等待。
   对比 netty 的线程模型，netty 采用了基于 NIO 和事件异步驱动的方式来处理，只需要通过少量的线程和 EventLoop 机制就可以处理大量的并发请求。它不会为每个请求创建一个线程，通过少量的线程来管理多个 IO 事件，从而极大避免了线程的上下文切换。

2. IO 模型：tomcat 采用的是 blockingIO，netty 采用的是 NIO。

取舍：

复杂度上升。同步模型代码简单，链路直观；异步模型在超时控制、异常传播、上下文传递、日志排查上都更复杂。我们的取舍是，网关是统一流量入口，稳定性和吞吐优先级高于实现复杂度，所以愿意接受更高的研发复杂度，换更高的性能上限和更好的资源利用率。

追问 1：Tomcat 现在也支持 NIO，为什么不直接使用 Tomcat 的 NIO 模式，而是整体换成 Netty？

答：Tomcat 的 NIO 只是底层 IO 改成 NIO，上层仍然是一请求一线程模型。即使 IO 是非阻塞，业务处理依然要占用独立线程，并发上来还是会产生大量线程，上下文切换的核心问题没有解决。Netty 的事件驱动模型可以做到业务异步化，不需要每个请求独占线程，这是本质差异。

追问 2：迁移 Netty 有没有遇到什么坑？

答：最大的挑战是异步编程模型带来的回调复杂度，需要妥善处理异常、超时、内存泄漏。同步代码的异常链路很直观，而异步回调如果处理不当，容易丢失异常，或者回调不触发造成内存堆积。我们增加统一回调埋点、异步请求强制超时机制来兜底。

追问 3：EventLoop 线程池怎么配置？EventLoop 能不能执行业务逻辑？

答：EventLoop 线程是 IO 线程，绝对不能执行耗时业务逻辑，否则会阻塞 IO 事件处理。业务计算、下游调用任务会提交到独立业务线程池，和 EventLoop IO 线程做隔离，保证 IO 事件处理不被业务阻塞。

客户端
    初始化:

为什么tomcat 要用那么多线程去进行处理, 而netty 用几个线程就可以去完成同样的事情

1. IO 模型上的差异
    1. tomcat 是基于blocking IO 来实现的, 每个HTTP 请求创建一个独立的线程来做的, 如果线程被阻塞住了, 会导致无法处理其他任务. 为了保证高并发下可以去处理, tomcat 需要在配置足够多的线程去预先准备好, 但是线程数过多后会导致线程的上下文切换和内存开销, netty 是基于 NIO 和 事件驱动机制来做的, 不用为每个请求去创建一个线程去处理
1. 事件驱动的设计
    因为netty 是基于reactor 的事件驱动模型,worker 不处理整个请求的生命周期, 只响应或底层发出的网络事件, 使得只有事件触发的时候才去执行任务, 而不是阻塞等待
2. 非阻塞 I/O
    netty 使用的NIO 为非阻塞IO, selector 机制: 通过NIO的selector的机制, netty 可以让worker 线程管理多个channel, 当selector监听到某个channel 有IO 事件的时候, 该线程才会去处理这个channel, 在没有事件时, 线程会去监听而不被阻塞
3. 任务划分与分离
    bossGroup 和 workerGroup 的职责分离, bossGroup 专门处理连接的建立和关闭, 而worker Group 专注于处理已建立的连接的读写操作. 从而避免了线程资源的抢占
4. 避免线程上下文的切换. 
    IO 的多路复用技术, 可以让一个线程监听多个channel 上的事件, 当channel 准备好读写的时候, 线程可以立即处理, 从而显著减少了线程数量

netty 的几个概念

EventLoop

EventLoop 本质上是 Netty 的事件循环执行器，通常会绑定一个线程，负责轮询 IO 事件，同时执行普通任务和定时任务。一个 EventLoop 可以管理多个 Channel，但一个 Channel 在生命周期内只会绑定到一个EventLoop 上。这样设计的好处是，同一条连接上的 IO 事件和任务处理都在同一个线程里串行执行，可以减少并发竞争和加锁开销。
eventLoop 如何管理多Channel 不卡顿: 一个eventloop 通过selector 监听多个channel 的 io 事件,只有当Channel 有可读可写事件才会触发再去进行处理, 同时netty 的 IO 逻辑相对轻量, 只要把耗时长的操作进行剥离, 就可以实现对大量 channel 的管理

Channel

Channel 是 Netty 对网络连接或者 IO 通道的抽象。比如服务端监听端口时会有 ServerSocketChannel，真正建立连接后会有对应的 SocketChannel。Channel 负责承载这条连接上的读写、连接状态、关闭等操作，可以理解成网络通信的载体。
可以通过Channel 中的 attr 去进行绑定一些数据

ChannelPipeline

ChannelPipeline 可以理解成 Channel 对应的一条处理链。每个 Channel 都会绑定一个 Pipeline，网络数据进来之后，会沿着这条链依次经过多个 Handler 做处理；数据写出去时，也会沿着这条链反向经过一系列Handler。它的作用就是把编解码、协议处理、业务逻辑、异常处理这些步骤串起来，形成职责清晰的处理流程。

ChannelHandler

ChannelHandler 是挂在 Pipeline 上的具体处理器，用来处理某一类事件或者某一段逻辑。比如有的 Handler负责解码，有的负责编码，有的负责业务逻辑，有的负责异常处理。不同的 Handler 各自职责单一，组合起来完成整条链路的处理。

如果把它们关系串起来理解的话：
  • Channel 是一条连接或者一个 IO 通道；
  • EventLoop 负责驱动这个 Channel 上的 IO 事件和任务执行；
  • ChannelPipeline 是这个 Channel 的处理链；
  • ChannelHandler 是处理链上的具体处理单元。

网关后端机器的CAP 是怎么考虑的, 为什么要用zk

我们当时选择 ZK，而不是 Eureka，核心原因是网关作为核心流量入口，对服务实例列表、路由配置、权重和规则变更的正确性要求比较高。如果注册中心在实例上下线、配置变更或者节点异常时出现较长时间的不一致，网关就可能把请求转发到错误实例、失效实例，或者继续使用过期规则，这对金融场景风险比较大。从 CAP 的取向上看，ZK 更偏 CP，能够更好保证这类关键元数据的一致性；而 Eureka 更偏 AP，在网络分区时更强调可用性，可能会在一段时间内保留不够准确的实例视图。对我们来说，这里的取舍是接受一定的可用性损失，换服务注册数据和配置视图的一致性，从而降低错误路由、错误转发和规则失效带来的风险。
而是因为网关依赖的注册发现和配置元数据对一致性要求更高，因此我们在这个场景下更倾向选择 ZK

网关自身的灰度特性, 灰度机器的配置下发

网关作为流量入口，一旦用户配置错误，会直接影响全量流量，故障影响面很大。为此我们设计了网关配置灰度发布机制，将配置出错引发的故障率降低 70%。
方案是在网关集群中独立部署灰度节点，将1% 的线上流量路由到灰度机器。用户变更网关配置后，先发布到灰度节点进行验证，通过观测灰度节点的流量、响应、错误指标，确认配置生效且行为符合预期；验证无误后，再把配置全量同步到生产网关集群。一旦灰度验证发现异常，可以快速回滚灰度配置，错误只会影响这 1% 流量，避免错误配置直接全量上线引发大面积故障

GC 算法

1. CMS
    1. 初始标记
        从GCRoots 出发的直接可达性对象, 需要进行STW, 
    2. 并发标记
        在初始标记的基础上, 标记处内存中所有的可达性对象, 此时没有进行STW, 用户线程和GC 线程同时在运行.
    3. 重新标记	
        需要进行STW, 对并发标记遗漏的对象进行修正, 在并发标记起期间产生的不可达对象需要在下一次GC 周期才能被回收
    4. 并发清除
        清除所有未被标记的对象, 进行对象回收, GC 线程和 用户线程同时在运行
    缺点: 
        1. 碎片化验证, 清除过程中不对内存进行压缩整理, 导致内存碎片话严重
        1.1 影响: 碎片化严重, 可能会导致老年代无法分配达对象, 触发full GC
        2. 浮动垃圾: 在并发标记期间产生的垃圾, 无法在当前GC周期被清除, 只能等到下一次GC
        2.1 影响: GC 效果不如预期, 需要预留更多的内存空间
        3. 某些情况下会退化成单线程回收
        3.1 如果堆内存不足以支撑程序的内存分配, 进而出发一次Full GC
        3.2 年轻代向老年代晋升, 如果老年代没有足够的空间去容纳这些对象的时候, 也会导致CMS 失败, 从而退化成单线程的Serial Old 收集器
        3.3 空间碎片化, 由于CMS 回收产生的碎片化, 导致大对象无法找到连续的内存进行分配, 最终触发full GC

                清点出有存活的对象和没有存活的对象
        3. 复制阶段
            重新分配对象内存和复制成员变量, 转移的时候需要进行STW, 复制的耗时和存活对象的数量以及对象的复杂程度成正比
          
        **初始标记**
            标记从GC Roots 出发的可达对象 需要进行STW
        - **并发标记**
            标记整个堆中的存活对象, 不会进行STW
        - **最终标记**
            完成并发标记, 并且处理在并发标记期间导致应用对象的变化, 需要进行STW
        - **筛选回收**
            确定进行回收, 并根据收集的数据区域进行回收
        - **拷贝回收**
            将存活的对象从回收区拷贝到新的区块, 方便进行回收
            特点:
                region 管理, 每个区域可能是Eden 区, 也可能是Survivor区, 也可能是old区
                并发标记和整理, 支持并发标记, 降低了STW 
                可预测的停顿时间
                优先回收: 维护一个优先队列, 根据各个区域回收的价值(回收成本和收益) 决定哪些要优先回收
            G1 怎么解决浮动垃圾:
                将对分割成多个region, 更加灵活的去管理和回收内存, 降低浮动垃圾的影响
                垃圾回收的时候, 可以进行并发标记和整理, 最大限度的降低程序的停顿

MGR 原理

1. 基于 Paxos 分布式一致性协议和自动化故障恢复机制, 允许多个Mysql 服务器组成一个复制组, 实现高可用性和容错能力

1.2 所有写操作都是需要经过所有组员的一致同意, 写操作先在主节点上提交, 主节点会通过 GTID (全局事物ID) 将事物广播给其他节点, 只有多数节点同意了, 事物才是被认为可执行的

                    冲突检测: 当一个节点尝试提交事物的时候, 会将该事物的write-set 与组内其他节点已提交但未应用的事物write-set 进行比较, 判断是否有冲突发生

GC 算法

1. 不过 G1 为了解决 CMS 并发清理导致内存碎片化的问题，使用了复制算法转移对象，这样如果在转移过程中 GC 线程和用户线程并行，会导致指针无法准确定位对象的问题

2.  zgc: 采用内存分区，使用染色指针和读屏障解决了复制算法并发转移对象导致的指针无法准确定位对象的问题
染色指针: 每个对象的指针在存储时都包含了附加的信息，用于表示对象的状态，比如是否是可达对象、是否需要被回收等
读屏障: 在 ZGC 中，读屏障用于捕获并记录正在被并发标记的对象引用，以便在后续的并发标记阶段中正确地标记这些对象。读屏障能够保证并发标记的准确性，防止对象在标记过程中被移动或修改引用关系导致的错误标记。
