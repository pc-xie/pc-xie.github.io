面试最后冲刺清单

面试最后冲刺清单

使用方式

这份文档不是完整题库，而是面试前最后过一遍的风险题清单。

重点目标有三个：

  1. 统一口径，避免数字和表述前后不一致
  2. 补齐风险题，尤其是 MQ、带人、Owner、一致性
  3. 所有回答都尽量落回基建、稳定性、核心链路、技术 Owner

一、最容易失分的 15 个问题

1. 你在项目里怎么体现技术 Owner？

我的体现主要有三点。
第一，我不是只接收需求做实现，而是会先识别主链路的核心瓶颈，比如网关里是线程模型和故障扩散问题，聚合链路里是串行调用、资源争抢和下游抖动问题。
第二，我会负责关键方案取舍，比如并行还是串行、线程池是否隔离、是否引入 Semaphore、什么时候做缓存兜底、什么时候做灰度。
第三，我会把方案一直跟到灰度、上线、指标验证和后续调优，确保结果闭环，而不是停留在设计层面。

2. 你没有正式带过团队，怎么证明自己有 TL 潜力？

我目前没有正式带过完整团队，这点我会坦诚说明。
但我有过虚线带实习生、带新人，以及在项目里承担方案设计、任务拆分、Code Review 和问题兜底的经历。
所以从行政管理角度看，我经验还不完整；但从技术 owner 和项目推进角度看，我已经在承担一部分类似 TL 的职责。

3. 你怎么带实习生或者新人？

我带实习生时，重点不是直接分配任务，而是先把背景、目标和边界讲清楚，再把任务拆到他能承接的粒度。
中间我会定期看实现思路和阶段结果，避免方向偏掉。
最后通过 Code Review 帮他把代码结构、异常处理、日志和测试这些质量问题收口。

4. 你怎么做 Code Review？

我做 Code Review 主要看五个点：主流程是否清晰、边界条件是否完整、异常处理是否收口、日志和监控是否足够、变更是否会影响线上稳定性。
如果是核心链路，我还会特别关注资源释放、超时处理、并发安全和灰度风险。
我的习惯是不只是看功能对不对，也会看后续维护成本和线上风险。

5. 你做过哪些复盘或者稳定性治理？

我做稳定性治理，不是只在事故后修问题，而是把一些能力前置和体系化。
比如线程池隔离、Semaphore 并发配额、差异化超时、分级熔断、缓存兜底、探针恢复、灰度发布、链路追踪和关键指标监控，这些都属于长期治理手段。
如果线上出现问题，我会按照先止血、再定位、再补长期机制的思路去做。

6. 你没做过 MQ，怎么回答？

我没有主导过 MQ 基础设施或者消息平台本身的建设，这不是我最强的方向。
但我对 MQ 的典型问题有系统理解，比如异步解耦、削峰填谷、重复消费、幂等、积压、顺序性和最终一致性。
如果岗位里会涉及，我不会把它包装成自己的核心亮点，但我有信心结合已有的高并发和稳定性经验比较快补上。

7. MQ 主要解决什么问题？

MQ 主要解决三个问题：异步解耦、削峰填谷和最终一致性。
它适合把一些不要求同步完成的链路拆开，降低上下游耦合，并在流量高峰时平滑处理请求。
代价是会引入重复消费、积压、顺序性和延迟这些新的问题，所以本质上是用系统复杂度换解耦能力和抗峰值能力。

8. 为什么会重复消费？幂等怎么做？

重复消费通常是因为生产确认、Broker 重试或者消费端处理失败重投导致的。
所以工程上很少追求绝对不重复，而是要求消费端具备幂等性。
常见做法是使用业务唯一 ID、防重表、唯一索引、Redis 去重或者状态机来保证重复执行不会产生副作用。

9. 消息积压怎么处理？

先判断是短期突发流量，还是消费能力长期不足。
如果是短期积压，可以临时扩容消费者、提高并发消费能力、优化消费速度。
如果是持续积压，就要检查消费逻辑是否过重、下游依赖是否变慢、消息体是否过大，以及 topic 或 partition 设计是否合理。

10. 缓存和数据库一致性怎么保证？

常见场景下我会优先用更新数据库、删除缓存的思路，而不是直接更新缓存。
因为缓存很多时候是聚合结果或者派生数据，直接更新缓存的复杂度和出错概率都更高。
如果对一致性要求更高，还需要结合延迟双删、重试、消息通知或者补偿机制来降低并发读写带来的脏数据风险。

11. Redis 高可用怎么理解？

Redis 高可用一般从主从复制、哨兵和集群三个层面理解。
主从复制解决读扩展和基础容灾，哨兵负责主观下线、客观下线、故障转移和新主选举，集群则进一步解决容量扩展和分片问题。
真正上线时还要关注脑裂、复制延迟、热点 key 和持久化策略。

12. MySQL 主从和事务隔离怎么答？

MySQL 主从主要是主库写 binlog，从库拉取并重放 relay log，从而保持数据复制。
事务隔离级别要掌握读未提交、读已提交、可重复读和串行化。
如果被问幻读，核心点是 InnoDB 在可重复读下会通过 MVCC 和 next-key lock 去降低问题。

13. 为什么你适合这个基建岗位？

因为我过去几年的经历主线很一致，都是围绕核心基础链路做高并发、高可用、稳定性和性能治理。
我做过网关、配置中心和多下游聚合链路，这些和岗位里提到的网关、注册配置中心、稳定性平台、容量与性能都高度相关。
我既能讲方案，也能讲落地和线上效果，这点和这个岗位要求比较匹配。

14. 为什么想换工作？

我换工作的核心原因，是希望继续往基础架构和技术中台方向深入发展，承担更完整的技术 Owner 职责。
我过去的经历让我比较明确自己更适合做核心基础系统，而不是纯业务功能开发。
所以我更看重的是岗位能否让我继续在网关、配置中心、稳定性治理这些方向做深。

15. 你最大的短板是什么？

如果说短板，我会比较坦诚地说两点。
第一，我没有正式带过一个完整团队，更多是虚线带人和项目推动；
第二，MQ 不是我过去最核心的方向。
但我不会回避这两点，一方面我已经在项目里承担了部分技术 owner 职责，另一方面 MQ 涉及的很多问题和我已有的高并发、隔离、稳定性思路是相通的。

三、每题一句标准答法

1. 为什么线程池隔离之后还要 Semaphore？

线程池解决的是服务内部线程资源隔离，Semaphore 解决的是对下游的并发请求量控制，两者一个保护自己，一个保护依赖。

2. 异步 IO、线程池、Semaphore 三者关系是什么？

线程池隔离内部资源，异步 IO 提升线程利用率，Semaphore 保护下游依赖，三者一起构成多层防护。

3. 为什么 GC 优化不先调 JVM 参数？

因为调参数只能延后问题，真正的根因是对象分配模型和装配方式，所以要先从代码结构和对象生命周期上解决。

4. 分级熔断和缓存的取舍是什么？

本质上是牺牲一部分实时性和实现复杂度，换下游异常时的整体可用性和收益稳定性。

5. 为什么选 ZK 不选 Eureka？

因为网关依赖的服务注册和配置元数据对一致性要求更高，错误视图的代价很大，所以我们更倾向选择偏 CP 的 ZK。

6. 为什么网关要从 Tomcat 切到 Netty？

因为网关是典型的 I/O 密集型系统，瓶颈在阻塞等待和线程占用，Netty 更适合高并发网络转发场景。

7. 为什么并行聚合不是简单的串行改并行？

因为真正要解决的不只是耗时叠加，还有资源争抢、故障扩散、下游保护和整体稳定性问题。

8. 为什么你说自己适合基建？

因为我长期做的都是核心基础链路，像网关、配置中心和高并发聚合链路，这些经历和基建岗位要求的方向高度一致。

五、供应链高频场景题

1. 如果让你做库存扣减，怎么防超卖？

我会把防超卖分成三层。
第一层是数据库层的强约束，比如 available_stock >= 扣减数量 的条件更新，或者基于版本号的乐观锁，保证并发场景下不会把库存扣成负数。
第二层是业务层幂等，给每次扣减带业务唯一单号，比如订单号或者扣减流水号，避免重试或者重复请求导致重复扣减。
第三层是链路层削峰和隔离，如果是大促场景，可以先通过 Redis 预扣或者 MQ 削峰，把瞬时流量打散，再异步落库。
如果是供应链场景，我还会区分总库存、可售库存、锁定库存三种状态。用户下单先锁库存，支付成功再正式扣减，超时未支付则释放锁定库存。这样既能防超卖，也能兼顾支付链路的最终一致性。

常见追问

  1. 为什么不能只靠 Redis 扣库存？
    Redis 更适合做预扣和削峰，但数据库才是最终账本。只靠 Redis，遇到回写失败、重启恢复或者异常补偿时，容易出现账实不一致，所以 Redis 负责抗高并发，数据库负责最终兜底。
  2. 乐观锁和条件更新怎么选？
    库存扣减我更偏向条件更新，比如 available_stock >= x，实现更直接，语义也更清晰。乐观锁更适合更新逻辑复杂、需要显式感知版本冲突的场景。
  3. 锁库存超时怎么释放？
    锁库存一定要带过期时间，通常结合延迟消息、定时任务或者支付超时扫描来释放。释放时还要先校验订单状态，避免支付已经成功却被误释放。
  4. 怎么避免重复扣减？
    关键是业务幂等。每次扣减都带订单号或扣减流水号，服务端落幂等记录或者唯一索引，重复请求直接返回已有结果，而不是再次扣减。
  5. 如果支付成功了，后面还有可能发现超卖吗？
    有可能，但取决于库存控制放在哪一层。如果系统是下单先锁库存、支付成功再确认扣减，正常情况下支付后不应该再发现超卖；如果是支付后才真正扣库存，就完全可能出现支付成功但库存不足。即使做了锁库存，如果并发控制、幂等、释放逻辑没做好，也可能因为实现漏洞导致异常，所以工程上重点是把超卖风险尽量前移到支付之前。
  6. 超卖风险尽量前移到支付之前，具体怎么做？
    核心就是不要等用户付完钱才第一次确认库存，而是在下单阶段先锁库存。只有锁库存成功，订单才能进入待支付；锁失败就直接提示库存不足。实现上通常会把可售库存转成锁定库存，并配合数据库条件更新或乐观锁保证并发安全；同时给锁库存设置过期时间，支付超时自动释放。支付成功后做的不是重新抢库存，而是把已经锁住的库存正式确认扣减。这样库存风险会在下单阶段暴露，而不是等用户付款后才发现没货。
  7. 如果大促时数据库已经扛不住怎么办？
    那就不能让所有请求直接打数据库。前面要加限流、预扣、队列削峰和热点隔离，把瞬时流量打散，数据库只承接最终确认流量。

2. 订单、库存、支付更新失败，怎么保证最终一致性？

我的思路不是追求一个大事务把三者强行绑死，而是用状态机加事件驱动去保证最终一致性。
典型做法是订单创建成功后，先落本地事务和事件消息，比如生成订单待支付状态，同时记录库存锁定事件。后续支付成功、库存扣减成功、履约成功，都是一步步驱动状态流转。
如果某一步失败，比如支付成功了但库存确认失败，就进入补偿链路：要么回滚订单和库存锁定，要么标记异常订单，由补偿任务或者消息重试继续推进。
这里最关键的几个点是：消息要保证可靠投递，消费端要保证幂等，状态流转要可追踪，补偿逻辑要能多次执行而不产生副作用。这样即使短时间内订单、库存、支付状态不一致，最终也能收敛到正确状态。

常见追问

  1. 为什么不用分布式事务把三者绑在一起？
    因为订单、库存、支付跨多个系统，强行用大事务会带来长事务、锁放大和可用性下降。供应链场景更常见的做法是局部短事务加异步补偿，用最终一致性换整体可用性。
  2. 消息怎么保证不丢？
    我会用本地消息表或者 Outbox 思路，把业务变更和待发送事件放在同一个本地事务里，先保证本地落库成功，再异步投递 MQ，失败持续重试。
  3. 消费重复怎么办？
    MQ 更常见的是至少一次投递，所以消费端必须做幂等。一般基于业务单号、唯一索引或者状态机控制，保证重复消费不会产生额外副作用。
  4. 补偿一直失败怎么办？
    不能只靠无限重试。常规做法是有限次自动重试，失败后进入死信、异常单或者人工介入池，保证问题可见、可追踪、可处理。
  5. 怎么判断最终一致性方案设计得够不够完整？
    我会重点看四点：状态机是否清晰，消息是否可靠，幂等是否到位，补偿和对账是否闭环。只要这四块打通，短暂不一致通常都能收敛。

3. 第三方物流状态回传延迟、重复、乱序，怎么处理？

这种问题我会拆成三个层面处理。
第一是幂等，物流方重复推送同一个状态是常态，所以会基于 运单号 + 状态码 + 时间戳/流水号 做幂等去重，避免重复更新。
第二是状态机校验，不是收到什么状态都直接覆盖，而是先判断当前订单是否允许流转到目标状态。比如已经签收的订单，不能再被更新回运输中。
第三是乱序处理，如果物流回传存在延迟和乱序，就要给每条状态带上业务时间或序列号，只接受更新鲜或者更高阶段的状态，旧状态直接丢弃或者只做日志记录。
如果第三方质量比较差，我还会增加主动拉取兜底，比如回传异常时定时主动查询物流轨迹，和推送结果做对账，避免完全依赖外部回调。

常见追问

  1. 没有序列号怎么处理乱序？
    那我会退一步用状态阶段和业务时间双重判断。比如签收一定高于运输中，旧阶段不能覆盖新阶段，时间戳只是辅助，真正兜底的是状态机合法性校验。
  2. 为什么不能收到状态就直接覆盖？
    因为第三方经常会重复、延迟甚至乱序回传，直接覆盖可能把已签收写回运输中，所以必须先做状态机校验，再决定是否更新。
  3. 如果回调丢了怎么办？
    不能完全依赖推送，要有主动拉取兜底。比如长时间没有收到关键物流节点，就按运单号主动查询轨迹，再和本地状态做对账修正。
  4. 重复推送怎么去重？
    一般基于 运单号 + 状态码 + 时间戳/流水号 做幂等键，或者对第三方回执流水做防重。核心目标是重复处理不产生额外状态变更。
  5. 第三方接口质量很差怎么办？
    除了接口治理，还要在业务上做降级和兜底，比如展示最近一次可信状态、延后用户可见更新、保留人工处理入口，避免把外部不稳定直接暴露给主流程。

4. 高峰期订单暴增时，系统怎么扛住？

核心思路是分层抗压，而不是只靠扩容。
入口层先做限流和降级，保护核心下单链路，像非核心推荐、埋点、弱依赖查询都可以降级。
应用层做异步解耦，把订单创建、库存扣减、履约通知、积分发放这类流程拆开，核心主链路先快速返回，非核心动作通过 MQ 异步处理。
资源层做隔离，比如订单、库存、物流、通知分别独立线程池或消费组，避免某个慢依赖把整个系统拖垮。
数据层重点保护库存和订单库，避免热点行竞争、慢 SQL 和数据库连接打满。如果是秒杀或者活动场景，还要提前做热点商品隔离、缓存预热和库存预扣。
本质上是通过限流、削峰、异步、隔离和降级，把流量高峰平滑掉，优先保住下单、支付、库存这些最核心链路。

常见追问

  1. 是不是多扩几台机器就行？
    扩容只是手段，不是根因解法。高峰期真正的问题往往是热点库存、数据库锁竞争、下游慢依赖和故障扩散，所以必须配合限流、削峰、隔离和降级一起做。
  2. 高峰期优先保什么？
    我会优先保下单、支付、库存这三条主链路。推荐、积分、埋点、短信、非关键查询都可以异步化或者降级，先保证交易闭环活下来。
  3. 热点商品怎么处理？
    热点商品不能直接把压力打到数据库热点行上，通常要做库存预扣、缓存预热、热点隔离，必要时把热点活动链路单独拆出来保护。
  4. MQ 本身积压怎么办？
    先判断是短期洪峰还是消费能力不足。短期可以扩消费者、提并发；如果是长期积压，就要检查消费逻辑是否过重、下游是否变慢、分区和 topic 设计是否合理。
  5. 如果某个下游慢了，会不会把整体拖垮？
    所以资源隔离很重要。订单、库存、物流、通知都应该分线程池、分消费组，必要时再加超时和熔断，避免一个慢依赖拖死全链路。

5. 如果仓库/物流商接口不稳定，如何做降级和补偿？

我会先区分核心动作和非核心动作。
如果是创建出库单、确认履约这种核心动作，不能因为第三方短时抖动就直接丢掉请求，所以一般会先落本地任务表或者消息队列，调用失败后自动重试，并配合人工可见的异常单。
如果是物流轨迹查询、预计到达时间这类弱实时接口，就可以直接走缓存兜底或者返回上次结果，避免把下游故障放大成主链路不可用。
在治理手段上，我会加超时、限流、熔断和隔离。比如某个物流商 RT 抖动明显，就快速失败，避免线程和连接长期堆积；同时保留缓存、重试和补偿任务做后续修复。
补偿层面通常有两类：一类是定时补偿，扫描失败记录重试；另一类是对账补偿，把仓库/WMS/物流/TMS 的状态和我们本地订单状态做比对，发现缺失或不一致时再触发修正。这样可以保证即使外部接口不稳定，主流程也尽量可用，最终数据也能收敛。

常见追问

  1. 超时和重试怎么设才合理？
    我会先设短超时，避免线程长期阻塞；重试只针对明确可重试错误，而且要限制次数并加退避，不能把下游短时抖动放大成重试风暴。
  2. 什么情况下要熔断？
    当错误率、超时率或者 RT 持续恶化时，就要快速熔断保护自己。熔断后核心动作先落任务表或消息队列，弱实时能力走缓存或上次结果。
  3. 核心动作失败了为什么不直接报错给用户？
    因为像出库、履约确认这类动作很多时候可以异步补偿，直接失败会把外部系统抖动放大成用户侧故障。更合理的是先把请求安全落下来，再后台推进。
  4. 补偿具体怎么落地？
    一个是失败重试，扫任务表重新调用；一个是对账补偿，定时比对仓库、物流和本地订单状态，发现缺口后再触发修正。
  5. 怎么判断降级和补偿方案是否靠谱？
    我会看三点：主流程是否还能继续、异常是否可见、数据最终能否收敛。只要这三点成立，方案通常就比较稳。

六、面试前 10 分钟速记

自我介绍主线

我是做基础架构和技术中台的，主线是网关、配置中心、稳定性治理和核心链路性能优化。

一句收尾

我最擅长的不是某一个中间件本身，而是围绕核心链路做问题识别、方案设计、稳定性治理和线上效果闭环。

七、Halara 岗位高频问题

岗位特点：

  • 海外独立站商城核心系统
  • 高并发、高可用、稳定性、可扩展性
  • 端到端交付质量和效率
  • 对缓存、消息、异步处理、线上排障有要求

1. 你过去做的是广告、网关、配置中心，为什么适合电商核心系统？

我不会把自己包装成有完整电商域经验的人，但我过去做的都是核心链路和关键系统，本质上解决的是高并发、高可用、依赖多、异常容易扩散的问题。
像广告聚合链路，我解决的是多下游依赖导致的时延放大和稳定性问题；支付网关，我解决的是统一流量入口在高峰场景下的承载、隔离和故障恢复问题；配置中心，我解决的是大规模配置推送和稳定性治理问题。
这些能力迁移到独立站商城，本质上还是核心链路治理，只是业务对象从广告请求、支付接入、配置推送，变成了商品、购物车、下单、履约这些链路。

2. 你没有完整电商商品导购经验，这会不会是短板？

如果说短板，我会坦诚说我过去最强的主线不是导购和交易业务本身，而是复杂核心链路的性能和稳定性治理。
但这类岗位我能迁移的部分很明确：第一是高并发链路设计；第二是依赖治理和隔离；第三是缓存、异步、熔断、降级、灰度和可观测性；第四是问题定位和线上收敛能力。
业务规则我会尽快补，但系统治理能力是我过去几年的主战场。

3. 你怎么理解海外独立站商城的核心技术挑战？

我理解核心有四类。
第一是核心交易链路长，商品、价格、库存、优惠、订单、支付、物流之间耦合高；
第二是流量波动明显，大促、活动、热点商品会带来瞬时峰值；
第三是依赖多，既有内部系统依赖，也有支付、物流、风控、营销等外部依赖；
第四是业务结果敏感，接口慢或者不稳定，不只是技术指标差，而是会直接影响转化率和 GMV。
所以这类系统的关键不只是功能实现，而是如何把性能、稳定性、隔离和最终业务结果一起做好。

4. 如果让你做独立站商城核心系统，你最先关注哪些链路？

我会优先看四条链路：
第一是商品详情和首页等高频读链路，因为这决定用户访问体验；
第二是购物车和结算链路，因为这里容易引入价格、库存、优惠计算复杂度；
第三是下单和支付链路，因为这里直接影响交易闭环；
第四是订单履约和状态回传链路，因为这关系到后续用户体验和客服压力。
我的习惯是先抓主链路、关键指标和最容易放大故障的依赖点。

5. 大促或者热点活动时，系统怎么扛住？

我的思路还是分层抗压，而不是只靠扩容。
入口层做限流、降级和静态化兜底；
应用层把非核心动作异步化，比如通知、埋点、积分、推荐刷新；
资源层做线程池隔离、消费组隔离和下游并发控制；
数据层重点保护缓存、库存、订单和价格计算这些热点数据。
如果热点集中在少量商品或者活动页，还要做缓存预热、热点隔离和单独限流，避免一个活动把整体站点拖垮。

6. 你怎么理解缓存和 MQ 在商城系统里的作用？

缓存和 MQ 都是核心治理手段。
缓存主要解决高频读链路的问题，比如商品详情、活动配置、价格展示、推荐结果等，重点是抗高并发和降低数据库压力。
MQ 主要解决异步解耦、削峰填谷和最终一致性问题，比如订单创建后的通知、积分、营销、履约推进等。
我不会把它们当成万能手段，而是会同时关注缓存一致性、消息幂等、重复消费、积压和失败补偿这些问题。

7. 如果面试官问你有没有 MQ 实战，你怎么答？

我不会说 MQ 是我过去最强的主线，但我会明确说自己对 MQ 的典型问题有系统理解。
像异步解耦、幂等、重复消费、积压、顺序性和最终一致性，这些我都有准备。
而且从我过去的项目经验看，很多高并发和稳定性治理思路和 MQ 场景是共通的，比如削峰、隔离、失败重试、补偿和链路可观测性。
所以我不会把自己包装成 MQ 专家，但我能比较快承接这类系统设计。

8. 你怎么保障端到端交付质量和效率？

我理解这不只是把代码写完，而是要把整个交付链路做闭环。
我会先把需求边界和主链路梳理清楚，再识别最容易影响稳定性和交付风险的点；
方案上尽量提前考虑灰度、回滚、监控、告警和异常收口；
上线后看核心指标是否达到预期，不达预期就继续调优。
我过去做项目比较强调这一点，不是停留在设计或开发完成，而是看最终线上效果和业务结果。

9. 如果线上出了问题，你怎么排查？

我一般分三步。
第一步先止血，判断要不要降级、限流、熔断或者切流，先保证核心链路可用；
第二步定位，看是不是流量异常、线程池打满、缓存命中下降、数据库变慢、下游依赖抖动或者消息积压；
第三步补长期机制，不只是修这一次，还要把监控、隔离、配置、灰度或者补偿机制补齐。
这套思路在我过去的广告聚合、支付网关和配置中心里都做过。

10. 如果面试官追问“你过去的经历怎么迁移到商城”？

我会这样答：

广告聚合链路让我积累了多依赖并发调用、线程池隔离、异步 I/O、超时和降级能力；
支付网关让我积累了高流量入口、异步化改造、资源隔离、灰度和可观测性能力；
配置中心让我积累了大规模配置生效、单元化、长轮询推送和稳定性治理能力。
这些能力迁移到商城，就是去解决高并发访问、复杂依赖编排、热点流量、核心交易链路稳定性，以及线上快速定位和收敛的问题。

11. 这个岗位最可能追问你的薄弱项是什么？

主要有三类：
第一，完整电商域经验，比如商品、购物车、价格、订单、履约、售后；
第二，MQ 和最终一致性落地细节；
第三，状态机和订单履约编排经验。
这些地方不要硬说做过完整闭环，更稳的说法是：我在业务域上不是最强证据，但底层的方法论和系统治理能力是可以迁移的。

12. 这个岗位的最佳收口回答

如果让我总结我和这个岗位的匹配点，我会说：
我过去最强的不是某一个具体业务模块，而是围绕核心链路做高并发、高可用和稳定性治理。独立站商城虽然业务更重，但本质上同样是长链路、多依赖、强异常处理和高峰流量治理问题。对这类问题，我在广告分发、支付入口和配置中心里都有比较扎实的实战积累，这也是我最能迁移过来的价值。
