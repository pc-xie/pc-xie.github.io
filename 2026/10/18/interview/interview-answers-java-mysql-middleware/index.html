面试

Java基础

JVM

1. 简述JVM内存区域划分，堆和元空间的区别？
JVM运行时内存大致可以分成程序计数器、虚拟机栈、本地方法栈、堆和方法区。程序计数器、虚拟机栈、本地方法栈是线程私有的；堆和方法区是线程共享的。

其中程序计数器可以理解成当前线程执行字节码的位置指示器；虚拟机栈主要存方法调用过程中的栈帧，比如局部变量表、操作数栈这些；本地方法栈是给 Native 方法用的。堆主要存对象实例和数组，也是 GC 最关注的区域。方法区主要存类元信息、常量、静态变量、JIT 编译后的代码等。

如果继续问堆和元空间的区别，我会说，堆主要放对象实例，元空间主要放类元数据。还有一个很重要的区别是，堆属于 JVM 管理的内存，而元空间用的是本地内存。实际排查问题时也能看到两类不同的 OOM，比如堆溢出常见是 Java heap space，元空间溢出常见是 Metaspace。

2. Young GC、Full GC分别在什么条件触发？哪些情况对象会直接进入老年代？
Young GC 通常是 Eden 区满了之后触发，主要回收年轻代里那些朝生夕死的对象，频率相对高，但单次停顿一般比 Full GC 短很多。

Full GC 通常是老年代空间不足、元空间不足，或者某些垃圾回收器在回收失败时触发的，它的代价会更高，停顿也通常更明显，所以线上一般都比较关注 Full GC 次数和停顿时间。

对象直接进入老年代的情况，常见有几类。第一是大对象，太大了不适合在年轻代频繁复制；第二是对象存活时间比较长，经历多次 Young GC 后会晋升；第三是 Survivor 区放不下，或者动态年龄判断后发现一批对象应该提前晋升。面试里我一般会补一句，真正线上排查时，重点不是背参数，而是看为什么对象晋升速度异常快。

3. 说说你排查GC问题的完整流程，会用到哪些工具？
先判断到底是内存泄漏，还是正常业务流量下对象分配太快导致 GC 压力大。

通常我会按几个步骤来排查。第一步先看现象，比如接口 RT 是不是抖动、吞吐是不是下降、CPU 是不是升高、Full GC 是不是频繁。第二步看监控，重点关注堆使用率变化、Young GC 和 Full GC 频率、暂停时间、对象晋升速率这些指标。第三步分析 GC 日志，判断是 Young GC 过于频繁，还是老年代回收压力大，或者有没有晋升失败、并发回收失败这类问题。

如果怀疑内存泄漏，我会进一步 dump 堆，分析大对象和引用链，确认到底是谁持有了不该持有的对象。如果不是泄漏，而是对象分配速率太高，那就要回到代码和业务链路，看是不是有大量短命对象创建、缓存使用不当、线程池任务堆积，或者某些热点路径在不断分配临时对象。

工具上我一般会用 jstat 看 GC 统计，jmap 或 jcmd 导出堆信息，jstack 看线程状态，结合 MAT、Arthas、VisualVM 这类工具做进一步分析。如果是线上复杂问题，我会强调一句：调参数是最后一步，前面先把原因分清楚，不然很容易治标不治本。

4. Serializable是什么接口？serialVersionUID的作用？为什么它是标记接口？
Serializable 本质上是一个标记接口，它本身没有任何方法，实现它的意义是告诉 JVM，这个类是允许被序列化和反序列化的。

serialVersionUID 可以理解成这个类序列化版本的唯一标识。在反序列化的时候，JVM 会拿流里的版本号和当前类的版本号做比较，如果不一致，就可能抛出反序列化异常。所以线上开发里，如果一个类需要稳定序列化，通常都会显式定义 serialVersionUID，避免因为类结构调整导致兼容性问题。

至于为什么它是标记接口，是因为这里不需要业务方去实现某个行为方法，它只是声明一种能力，也就是“这个类可以被序列化”。真正的序列化逻辑不是由业务类自己完成的，而是由 JVM 和序列化框架来完成的。所以它设计成标记接口是比较自然的。

线程池

5. ThreadPoolExecutor有哪些核心参数？任务提交之后完整执行流程是什么？

线程池核心参数一共 7 个。corePoolSize 是核心线程数，可以理解成线程池平时常驻的线程数量。maximumPoolSize 是最大线程数，表示线程池在高峰期最多能扩到多少线程。keepAliveTime 是非核心线程的空闲存活时间，高峰过去之后，多出来的线程空闲一段时间会被回收。unit 就是这个时间的单位。workQueue 是任务阻塞队列，核心线程忙不过来时，新任务会先进入队列排队。threadFactory 是线程工厂，主要用来创建线程，实际开发里一般会自定义线程名，方便排查问题。handler 是拒绝策略，当线程数到上限并且队列也满了，再来新任务时就会走这里的处理逻辑。

第一步，先判断当前线程数是不是小于 corePoolSize。如果小于，线程池不会先排队，而是直接创建一个新的核心线程来执行这个任务。也就是说，在核心线程数还没占满之前，线程池优先扩核心线程。

第二步，如果当前线程数已经达到 corePoolSize，线程池就不会继续立刻创建新线程了，而是先尝试把任务放进 workQueue 阻塞队列。如果队列还有空间，任务就先进入队列等待，等前面的线程执行完已有任务之后，再从队列里把它取出来执行。

第三步，如果队列已经满了，线程池才会继续判断当前线程数是不是小于 maximumPoolSize。如果还没到最大线程数，线程池就会再创建一个非核心线程来处理这个新任务。也就是说，只有在‘核心线程用满了并且队列也满了’的前提下，线程池才会继续扩容到非核心线程。

第四步，如果当前线程数已经达到 maximumPoolSize，并且队列也满了，说明线程池已经没有更多处理能力了。这时候如果还有新任务提交进来，就不会再被正常接收，而是会触发拒绝策略，也就是交给 RejectedExecutionHandler 去处理，比如直接抛异常、调用者自己执行，或者丢弃任务

6. 线程池4种拒绝策略分别是什么，业务上如何选型？
JDK 默认有 4 种拒绝策略。第一种是 AbortPolicy，直接抛异常，这是最直接也最容易感知问题的一种。第二种是 CallerRunsPolicy，由提交任务的线程自己执行，相当于给调用方施加回压。第三种是 DiscardPolicy，直接丢弃任务，不抛异常。第四种是 DiscardOldestPolicy，丢弃队列里最老的任务，再尝试提交当前任务。

如果问业务上怎么选，我一般会从“任务能不能丢”来判断。如果是核心链路任务，不能悄悄丢，我一般会优先选 AbortPolicy，然后配合监控和告警及时发现问题。如果希望系统在高峰期自然降速，可以考虑 CallerRunsPolicy，因为它会把压力反推给调用方。如果是日志、埋点、监控上报这类允许部分丢失的任务，可以考虑 DiscardPolicy。DiscardOldestPolicy 我在线上相对用得少，因为它会悄悄把队列里已经排队的老任务丢掉，排查问题时不够直观。

7. 线程池使用无界队列会出现什么问题？为什么生产环境要用有界队列？
生产环境里线程池一般不建议用无界队列，因为它表面上很平稳，实际上容易把风险往后拖，最后拖成更大的问题。

无界队列最大的风险是任务会无限堆积。如果下游处理能力跟不上，请求还在不断进来，任务就会一直压在队列里，最终可能把内存打满，甚至直接 OOM。还有一个容易被忽略的问题是，一旦用了无界队列，maximumPoolSize 基本就失去意义了，因为任务通常会优先进队列，不太会继续扩线程。

所以生产环境更常见的做法是用有界队列。有界队列的价值在于，它能明确系统的容量上限，流量超出承载能力时，不会无限堆积，而是通过拒绝策略、降级、回压这些方式尽早暴露问题。我的理解是，线上系统最怕的不是失败，而是看起来没失败，实际上延迟越来越高，最后整体雪崩。

8. 线程池参数能不能直接网上抄模板？结合业务说说参数评估思路。
线程池参数不能照着网上模板直接抄，因为线程池本质上是一个容量管理工具，参数一定要结合业务特点来定。

我通常会先判断任务到底是 CPU 密集型还是 IO 密集型。CPU 密集型任务线程数一般不会配太大，通常接近 CPU 核数；IO 密集型因为有等待时间，线程数可以适当放大，但也不能无限放大，否则线程切换和资源竞争反而会把系统拖慢。

除了线程数，我还会看队列长度怎么配。队列长度不是越大越好，而是要结合峰值流量、任务平均耗时、可接受排队时延来估算。如果一个任务平均执行 200 毫秒，峰值流量又很高，那你就得想清楚系统允许排队多久，超过这个时间是不是应该直接拒绝。

如果结合项目来讲，我会补一句，比如网关里的鉴权、路由转发这种逻辑通常比较短平快，线程池参数会更保守，优先控制延迟和稳定性；如果是 RPC 聚合或者异步推送这种场景，就要更关注 IO 等待比例、下游承载能力以及超时隔离。我的习惯是先做理论估算，再压测验证，最后结合监控持续校正，而不是一次性拍脑袋定死。

Netty & IO

9. BIO、NIO、AIO三者区别，Netty为什么选择NIO/epoll模型？
BIO 是同步阻塞模型，最典型的特点就是一个连接通常对应一个线程，线程会阻塞在读写操作上。如果连接数上来了，线程数量也会跟着暴涨，线程切换和内存开销都会比较重。

NIO 是同步非阻塞，它的关键点是多路复用。一个线程可以通过 Selector 监听多个连接，只有某个连接真正有读写事件时，线程才去处理，所以资源利用率会高很多。

AIO 是异步非阻塞，应用线程发起请求之后不需要自己轮询，等操作系统把 IO 完成之后再回调通知。理论上它更彻底异步，但在 Java 生态里，AIO 的成熟度和普及度没有 NIO 高。

Netty 之所以主流上选择 NIO，尤其在 Linux 下配合 epoll，本质上是因为这套模型在高并发网络场景下更成熟、扩展性更好。它不需要像 BIO 那样为每个连接绑定一个线程，而是通过事件驱动和多路复用，用更少的线程支撑更多连接，所以很适合网关、RPC、长连接这类高并发场景。

10. Netty主从Reactor模型是什么？IO线程为什么不能执行业务耗时逻辑？
Netty 里典型的主从 Reactor 模型可以理解成两层线程组：BossGroup 负责接收连接，WorkerGroup 负责处理已经建立连接上的读写事件。这样做的好处是把连接接入和数据处理分开，避免所有事情都堆在一类线程上。

为什么 IO 线程不能做耗时业务，这个问题其实很关键。因为 IO 线程最重要的职责是处理网络事件，如果在里面做数据库查询、远程调用、复杂计算这些耗时操作，线程就会被长时间占住，后续别的连接上的读写事件也没法及时处理。结果就是事件循环被拖慢，连接堆积，RT 抖动，严重时甚至会导致超时和吞吐下降。

所以 Netty 的最佳实践通常是，IO 线程只做网络收发和协议编解码，真正耗时的业务逻辑交给独立的业务线程池去做。这样网络层和业务层的资源边界才是清晰的。

11. Netty池化ByteBuf和非池化ByteBuf区别？ByteBuf内存泄漏如何检测？
池化 ByteBuf 的核心价值是复用内存块，避免频繁申请和释放，尤其是在高并发场景下，可以明显减少内存分配开销和直接内存碎片问题。非池化 ByteBuf 实现上更简单，但每次都新建和释放，性能通常不如池化方案稳定。

所以在高并发网络程序里，Netty 很多场景都会优先使用池化内存，这样不仅性能更好，对 GC 压力也更友好。

至于内存泄漏，Netty 里常见的问题其实不是 Java 堆内存，而是引用计数对象没有正确释放，导致直接内存泄漏。排查时我一般会先看有没有开启 ResourceLeakDetector，再结合日志看是否有 LEAK 告警。同时重点检查自定义 handler 里有没有拿到 ByteBuf 之后没有及时 release()，因为这是最常见的泄漏来源。这个问题在线上排查时很典型，看起来 JVM 堆没满，但进程内存还是一直涨。

12. 什么是零拷贝，Netty如何实现零拷贝？
零拷贝的核心目标不是完全没有拷贝，而是尽量减少用户态和内核态之间不必要的数据复制，降低 CPU 开销，提高网络传输效率。

Netty 里常见的零拷贝实现主要有几类。比如文件传输时可以用 FileRegion 或 sendFile，减少文件数据在用户态和内核态之间来回拷贝。再比如 CompositeByteBuf，它可以把多个缓冲区在逻辑上拼成一个整体，而不是重新申请一块大内存把数据复制过去。还有 slice() 和 duplicate()，它们本质上是共享底层内存，只创建新的视图，所以也能避免数据复制。

如果面试时想收口，我一般会说，零拷贝本质上是用更少的数据搬运换更高的吞吐，这也是 Netty 适合高性能网络编程的重要原因之一。

多线程

13. synchronized和Lock的区别？简述锁升级过程：偏向锁、轻量级锁、重量级锁。
先讲 synchronized 和 Lock 的区别，再讲锁升级。

synchronized 是 Java 内置关键字，JVM 层面支持，使用上比较简单，进入同步块自动加锁，退出时自动释放锁。Lock 比如 ReentrantLock，是显式锁，功能更灵活，支持可中断获取、公平锁、超时获取、多个 Condition 这些高级能力，但需要自己在代码里手动释放。

所以如果是一般同步场景，synchronized 就够用了，语义清晰，也不容易忘记释放；如果场景更复杂，比如需要超时等待、可中断、公平性控制，那通常会选 Lock。

锁升级这一块，我一般会这么讲：如果基本没有竞争，JVM 会尽量用偏向锁，减少无意义的同步开销；如果开始出现线程竞争，但竞争不激烈，会进入轻量级锁阶段，主要靠 CAS 和自旋来获取锁；如果竞争再激烈，自旋也解决不了，就会升级成重量级锁，走操作系统层面的阻塞和唤醒。面试时我会顺带补一句，虽然新版本 JDK 里偏向锁机制已经逐渐弱化，但这套“从低开销到高开销”的升级思路还是理解锁优化的关键。

14. CompletableFuture如何处理异常？并行调用多个下游时如何处理单个任务失败？
这个问题我一般会先讲 API 层面的异常处理，再讲业务层面的容错思路。CompletableFuture 常见的异常处理方式有三个：exceptionally() 用于出现异常时给一个兜底结果；handle() 不管成功还是失败都会进入，适合统一转换结果；whenComplete() 更偏回调通知，通常用来记录日志或埋点，但不会直接改变结果。

如果是并行调用多个下游，关键不只是“会不会抛异常”，而是单个下游失败时，整体请求要不要失败。这个要看业务要求。如果允许部分失败，我一般会让每个子任务单独做超时和异常兜底，最后聚合时返回一个降级后的结果。如果业务要求必须全成功，那就可以用 allOf()，只要有一个失败，整体就按失败处理。

但在实际项目里，我更关注的是不要让一个慢依赖或者异常依赖把整个聚合接口拖死。所以通常会给每个子任务单独设置超时、异常转换和默认值，必要时再结合线程池隔离、熔断和缓存兜底。这样单点故障才不会演变成全链路故障。

MySQL数据库

1. MySQL四大事务隔离级别分别是什么，各自解决什么问题？
Read Uncommitted 是最低的隔离级别，连未提交的数据都可能读到，所以会有脏读问题。Read Committed 只能读到已提交的数据，解决了脏读，但同一个事务里前后两次读结果可能不一样，所以还会有不可重复读。Repeatable Read 是 MySQL InnoDB 默认的隔离级别，它能保证同一个事务里多次读取同一条记录结果一致，主要解决不可重复读问题。Serializable 是最高隔离级别，基本可以理解成强制串行执行，并发能力最差，但一致性最强。

隔离级别越高，一致性通常越强，但并发性能也越差，所以实际选型不是“越高越好”，而是看业务需要什么样的一致性和并发平衡。MySQL 默认用 RR，本质上就是在一致性和性能之间做了一个比较实用的取舍。

2. MVCC实现原理是什么？undo log、ReadView作用？RC与RR的ReadView有什么差异？
MVCC 本质上是多版本并发控制，它的核心目的是让读操作尽量不加锁，从而提升并发能力。它不是让所有事务都去抢同一把锁，而是让读请求去读一个对自己可见的数据版本。

这个机制能成立，主要依赖两个东西。一个是 undo log，更新数据时旧版本不会立刻消失，而是通过 undo log 串成版本链，这样事务在读的时候就有机会看到历史版本。另一个是 ReadView，它可以理解成当前事务的“可见性视图”，用来判断版本链上的哪个版本对当前事务是可见的。

RC 和 RR 最大的区别就在 ReadView 生成时机不同。RC 是每次快照读都会生成新的 ReadView，所以同一个事务里两次查询有可能读到不同结果；RR 通常是在事务里第一次快照读时生成 ReadView，后续复用，所以多次读取结果一致。面试时我一般会补一句，MySQL 的 RR 之所以表现比较好，很大程度上就是因为 MVCC 把很多读操作从加锁里解放出来了。

3. 什么是快照读、当前读？哪些SQL属于当前读？
快照读就是普通的 select，它读到的不一定是当前最新版本，而是 MVCC 机制下对当前事务可见的那个版本，所以一般不加锁，重点是提高并发读性能。

当前读就不一样了，它要读的是最新版本，而且通常会加锁，目的是保证后续更新时的数据一致性。典型的当前读包括 select ... for update、select ... lock in share mode 或 for share，以及 update、delete、insert 这类会直接修改数据的语句。

如果面试官问怎么理解，我会说，快照读更偏“高并发一致性读”，当前读更偏“我要改数据，所以得先把最新状态和锁控制住”。

4. InnoDB行锁什么情况下会退化为表锁？意向锁的作用是什么？
这个问题我一般会先纠正一个常见说法。严格来说，很多时候不是“行锁退化成表锁”，而是因为 SQL 没有走索引或者扫描范围过大，导致锁住了大量记录，最终表现出来很像表锁效果。

最典型的场景就是更新条件没命中索引，数据库只能全表扫描，那它加锁的范围就会非常大。还有一些范围查询场景里，Next-Key Lock 覆盖区间比较大，也会让人感觉像把整张表都锁住了。

意向锁的作用我一般会解释成“协调表锁和行锁”。因为 InnoDB 支持行级锁，如果一个事务准备给某些行加锁，它会先在表级别打一个意向锁，告诉别人“这张表里有些行我准备加锁了”。这样另一个事务如果想直接给整张表加表锁，就能快速判断是否冲突，而不用一行一行去检查。它本质上是一个加锁冲突判断优化机制。

5. redo log、undo log、binlog分别的作用，三者区别？
redo log 主要是保证事务的持久性。因为 MySQL 不可能每次提交事务都立刻把数据页刷盘，所以 InnoDB 会先把修改记录到 redo log 里。这样即使数据库宕机，重启后也可以根据 redo log 把已经提交但还没来得及落盘的数据恢复出来。

undo log 主要有两个作用。第一是事务回滚，如果事务执行失败或者主动回滚，可以根据 undo log 把数据恢复到修改前的状态；第二是配合 MVCC 保存旧版本数据，让快照读能够读到历史版本。

binlog 是 Server 层的逻辑日志，主要用于主从复制和数据恢复。比如主库执行了哪些增删改，都会以逻辑操作的形式记录到 binlog 里，从库就是靠它来同步数据的。

如果问三者区别，我会总结成一句话：redo log 偏崩溃恢复，undo log 偏回滚和多版本控制，binlog 偏复制和归档。再补充一点，redo log 是 InnoDB 引擎层日志，binlog 是 MySQL Server 层日志，这也是它们职责不同的根本原因。

6. 事务ACID四个特性分别依靠什么来实现？
原子性，也就是事务里的操作要么全成功，要么全失败，主要靠 undo log 来保证，因为失败时要能把已经执行的修改回滚掉。持久性指的是事务一旦提交，结果就不能丢，这主要靠 redo log 来保证，即使宕机也能恢复。隔离性指多个事务并发执行时，彼此之间不能互相干扰，这一块主要靠锁机制和 MVCC 来实现。一致性是最抽象的一层，它不是单纯靠某一个机制保证的，而是原子性、隔离性、持久性再加上业务约束共同作用的结果。

如果面试时想答得更完整，我会补一句：一致性其实是事务最终想达到的目标，而原子性、隔离性、持久性更像是数据库为了实现一致性提供的技术手段。

7. 慢SQL排查思路，索引失效常见场景有哪些？

第一步先定位具体是哪条 SQL 慢，这一块通常结合慢查询日志、APM 监控、数据库监控来做。第二步拿到 SQL 之后，用 EXPLAIN 去看执行计划，重点看有没有走索引、扫描行数大不大、有没有回表、有没有 Using filesort、Using temporary 这类额外开销。第三步再结合表结构和业务场景判断，到底是索引设计问题、SQL 写法问题，还是数据量增长、统计信息不准、锁等待这类问题。

索引失效的常见场景我一般会列几个高频点。比如对索引列做函数运算或表达式计算，可能导致索引失效；再比如隐式类型转换、联合索引没有满足最左前缀原则、like '%xx' 这种前缀模糊匹配，也经常导致走不上索引。另外 or 用得不合适、范围查询之后联合索引后续列利用率下降，也都是常见问题。

如果面试里结合项目，我会补一句，慢 SQL 排查不能只盯着“有没有索引”，更重要的是看执行计划和实际业务访问模式是否匹配，因为很多 SQL 不是没索引，而是索引设计得不对。

8. 大表数据持续膨胀，如何做冷热数据归档？
把高频在线访问的数据和低频历史数据分开，避免所有数据都堆在一张大表里。

常见做法是按时间维度做冷热分层。比如近三个月的数据保留在热表里，保证查询和写入性能；更早的数据迁移到归档表、历史库，甚至 ES、对象存储、离线数仓里。这样热数据表的索引体量更小，查询效率更稳定。

归档过程本身也要注意方式，不能直接一把大事务把几百万行迁走，不然很容易导致锁表、主从延迟甚至影响线上业务。一般会用定时任务分批迁移、分批删除，控制批次大小和执行时间窗口。应用层如果要查历史数据，可以通过路由规则或者中间层封装去兼容冷热表差异。

如果结合项目来讲，我会补一句，像配置中心的配置变更记录、网关访问日志、审计日志这些，天然就适合做按时间维度的冷热归档，因为线上高频查询通常只关心最近一段时间的数据。

9. 并发更新同一条记录，如何防止数据丢失覆盖，乐观锁怎么实现？
悲观锁和乐观锁。

悲观锁的思路是，我先假设冲突很可能发生，所以在更新前先把这条记录锁住，比如 select ... for update，这样同一时间只有一个事务能改。它的优点是强控制，缺点是并发能力相对差一些。

乐观锁的思路正好相反，它假设并发冲突不是特别频繁，所以不提前加锁，而是在更新时做版本校验。最常见的做法就是加一个 version 字段。比如我先查出当前版本是 5，更新时执行 update ... set version=6 where id=? and version=5，如果影响行数是 0，就说明这条数据在我更新之前已经被别人改过了，我这次更新就失败了，需要重试或者返回冲突。

如果问我怎么选，我一般会说，读多写少、冲突频率不高的场景更适合乐观锁，因为它并发性能更好；如果是强一致、高冲突更新场景，比如库存扣减这类，就要更谨慎地考虑悲观锁或者更严格的并发控制方案。

10. 分库分表适用什么场景，什么场景不需要分库分表，参考你的配置中心项目。
库分表解决的到底是什么问题。它本质上解决的是单库单表在数据量、写入压力、存储容量、索引维护成本上的瓶颈问题。当单表数据量特别大、单机 IO 扛不住、或者业务需要明显水平扩展时，分库分表才是合理选择。

但很多场景其实并不需要分库分表。比如数据量和 QPS 还远没到瓶颈，或者业务里有很多复杂查询、强一致事务需求，那过早分库分表反而会把系统复杂度拉得很高，带来跨分片查询、分布式事务、扩容迁移这些额外问题。

如果结合配置中心项目，我会说配置中心的核心数据通常没有大到必须靠分库分表才能活下去。它更常见的瓶颈往往不在数据库容量本身，而在配置推送链路、长轮询连接、本地缓存一致性这些地方。所以优先级通常是先做索引优化、读写分离、冷热归档、缓存，再看是否真的有必要拆库拆表。我的理解是，分库分表应该是最后的扩展手段之一，而不是默认动作。

中间件 & 网络技术基础

Zookeeper

1. ZAB协议的核心作用是什么？
ZAB 本质上是 ZooKeeper 用来保证分布式一致性的原子广播协议，它的核心作用有两个：一个是保证写请求在集群里的顺序一致，另一个是保证 Leader 宕机恢复之后，整个集群还能继续保持数据一致。

也就是说，ZAB 主要解决的是分布式场景下“崩溃恢复 + 有序广播”这两个问题。因为 ZooKeeper 这种协调型中间件，最怕的不是性能低一点，而是多个节点数据不一致。ZAB 就是为了解决这个问题设计的。

如果面试官继续追问，我会补一句，它背后的核心思想是通过 Leader 来统一串行化事务请求，然后把事务按顺序广播给 Follower，从而保证全局顺序一致。

2. ZK的节点类型：持久、临时、顺序节点，各自适用场景？
持久节点的特点是客户端断开后节点还在，适合存配置数据、注册元信息这类需要长期存在的数据。临时节点的特点是会跟客户端会话生命周期绑定，客户端一断开，这个节点就自动删除，所以很适合做服务注册、健康存活标识。顺序节点则是在创建时自动追加递增序号，适合做分布式锁、队列、选主这类需要顺序语义的场景。

如果再结合一下，我一般会提一句，实际项目里最常见的是“临时顺序节点”，因为它既能自动清理，又能带顺序性，所以非常适合做分布式锁和 Leader 选举。

3. ZK Watcher机制是什么？Watcher一次性触发，如何解决？
Watcher 可以理解成 ZooKeeper 的事件通知机制。客户端可以对某个节点注册监听，一旦节点数据变化、子节点变化或者节点状态变化，ZooKeeper 就会通知客户端。

但它有一个很重要的特点，就是一次性触发。也就是说，你注册一次 Watcher，触发一次之后这个监听关系就没了。如果后续还想继续监听，就需要重新注册。

所以在实际使用里，解决方式一般有两类。第一类是在客户端收到通知之后主动重新注册 Watcher；第二类是直接使用像 Curator 这样的客户端框架，由它帮你封装持续监听、自动重注册这些逻辑。我的理解是，Watcher 更适合做轻量级通知，不适合把它理解成一个可靠消息订阅系统。

4. ZK适合做哪些事情，不适合做哪些事情？
这个问题我一般会先讲 ZooKeeper 的定位。ZooKeeper 本质上是一个分布式协调组件，它适合存储小而关键的协调数据，比如服务注册发现、配置管理、分布式锁、Leader 选举、命名服务这些。

但它不适合拿大数据量、高频写入或者复杂查询的业务来做。因为 ZK 的设计重点不是海量数据存储，也不是高吞吐业务访问，而是强一致协调。如果把它当数据库、消息队列或者大流量 KV 来用，基本都会踩坑。

所以面试里我一般会收口成一句话：ZooKeeper 适合做协调，不适合做承载重业务数据的存储系统。

RPC(Dubbo、gRPC)

5. Dubbo完整调用流程，底层网络组件、常见序列化方案？
首先服务提供者启动之后，会把自己的服务信息注册到注册中心。服务消费者启动时会去订阅这些服务地址，并在本地生成代理对象。业务代码调用这个代理对象时，看起来像本地方法调用，实际上底层会经过负载均衡选择一个服务提供者，然后通过网络客户端把请求发出去。

服务端收到请求之后，会先做反序列化，再执行业务逻辑，执行完之后把结果序列化，通过网络返回给消费方，最后客户端再把结果还原成调用结果返回给业务代码。

底层网络组件在 Dubbo 里最常见的是 Netty，因为它在高并发网络通信场景下性能和成熟度都比较高。序列化方案常见的有 Hessian2、Kryo、Protobuf 等，选型通常要在性能、兼容性、跨语言能力之间做平衡。

6. Dubbo有哪几种负载均衡策略？
Dubbo 常见的负载均衡策略有 Random、RoundRobin、LeastActive、ConsistentHash。

Random 就是随机，通常也是默认比较常见的一种，简单直接，适合大多数通用场景。RoundRobin 是轮询，按顺序把请求分发到不同节点。LeastActive 是最少活跃调用数，也就是优先把请求分给当前处理压力更小的节点，这种策略在各节点耗时差异比较大的场景下会更合理。ConsistentHash 适合有会话粘性或者同一类请求希望尽量落到同一台机器上的场景。

如果面试官问我怎么选，我会说，大多数情况下随机就够了；如果节点处理时延差异大，可以考虑最少活跃；如果有粘性路由诉求，再考虑一致性哈希。

7. gRPC和Dubbo的主要差异？
gRPC 更偏标准化、跨语言 RPC 框架，它基于 HTTP/2，默认搭配 Protobuf，在多语言互通和流式通信上优势比较明显。Dubbo 更偏 Java 生态下的服务治理框架，除了 RPC 调用本身，它在服务注册发现、路由、负载均衡、容错这些微服务治理能力上会更完整。

所以如果是一个多语言团队，或者对跨语言通信、流式能力要求高，gRPC 往往更合适；如果主要是 Java 微服务体系，而且对服务治理能力要求高，Dubbo 通常会更顺手。

如果让我用一句话总结，我会说：gRPC 更像一个高性能的跨语言通信框架，Dubbo 更像一个面向 Java 微服务治理的 RPC 体系。

8. RPC调用的超时与重试，有哪些坑需要注意？
RPC 最怕的不是调用失败，而是超时和重试策略没设计好，把局部问题放大成系统级问题。

常见坑点有几个。第一，超时设置过大，会导致故障传播很慢，线程和连接被长时间占住；超时设置过小，又可能把正常抖动误判成失败。第二，重试如果没有幂等保障，可能导致重复下单、重复扣费这类严重问题。第三，多层服务都各自重试，很容易形成重试风暴，本来只是一个下游慢，最后整个链路都被打爆。

还有一种典型情况是，服务端其实已经执行成功了，只是客户端超时没收到响应，这时候如果客户端再重试，就会出现“服务端成功一次，客户端以为失败又再来一次”的重复执行问题。

所以我的做法一般是：先把超时拆清楚，比如连接超时、读取超时分别设置；然后只对幂等操作谨慎重试；重试次数要有限制，最好带退避策略；再配合熔断、限流、隔离一起用。重试本质上不是补救万能药，而是建立在幂等和容量边界之上的。

TCP / HTTP网络

9. TCP三次握手、四次挥手；TIME_WAIT、CLOSE_WAIT产生的原因，网关场景如何优化？
三次握手的本质是双方互相确认收发能力，并同步初始序列号。四次挥手是因为 TCP 是全双工的，双方关闭连接需要分别发送 FIN 和 ACK，所以通常是四次。

TIME_WAIT 通常出现在主动关闭连接的一方，它在发送最后一个 ACK 之后还要保留一段时间，主要是为了确保对方收到这个 ACK，同时让网络中的旧报文自然过期。CLOSE_WAIT 则通常说明被动关闭连接的一方已经收到了对方的 FIN，但本地应用还没有真正调用 close 把连接关掉。实际线上如果 CLOSE_WAIT 很多，通常要优先怀疑应用代码有没有连接没正确释放。

如果结合网关场景，我会说优化重点不是盲目调内核参数，而是先减少频繁建连和不规范关连。比如尽量使用连接池、长连接、keepalive，避免每个请求都重新建连；再检查应用层是否存在连接泄漏，特别是导致 CLOSE_WAIT 堆积的问题。内核参数可以调，但那通常是辅助手段，根本还是应用层连接管理要做好。

10. HTTP1.1 和 HTTP2 的区别，网关场景HTTP2带来哪些收益？
HTTP/1.1 主要特点是支持长连接，但本质上还是文本协议，而且一个连接上的请求处理效率有限，容易受到队头阻塞影响。HTTP/2 则是二进制分帧协议，支持多路复用、头部压缩，还支持服务端推送，不过推送在实际业务里用得不算特别多。

HTTP/2 对网关场景的价值主要在于多路复用。以前可能需要开很多连接才能并发多个请求，现在一个连接就可以并发传多个请求，这样可以减少连接数量、降低握手和 TLS 开销，对弱网、高并发、跨地域场景尤其有帮助。

所以如果面试官问收益，我会总结成三点：连接更省、传输效率更高、弱网和高并发场景下体验更稳定。

11. TCP滑动窗口、拥塞控制简单说明。
这个问题我一般会把流量控制和拥塞控制分开讲。滑动窗口主要解决的是“接收方吃不吃得消”的问题。接收方会告诉发送方自己当前还能接收多少数据，发送方就按照这个窗口大小来发，避免对方来不及处理。

拥塞控制解决的是“网络吃不吃得消”的问题。即使接收方还能收，如果整个网络链路已经拥堵了，发送方也不能无限发，否则只会让拥塞更严重。所以 TCP 会根据网络状况动态调整发送速率。

常见的拥塞控制过程可以简单理解成慢启动、拥塞避免、快重传、快恢复。面试时我一般不会展开算法细节太多，而是先把这两个控制维度讲清楚，因为这才是面试官更想确认你是否理解的重点。

12. 长轮询和WebSocket的区别，配置中心为什么选用长轮询？
长轮询本质上还是 HTTP 请求，只是客户端发起请求后，如果服务端暂时没有新数据，就把这个请求挂一会儿，等有变更或者超时再返回，客户端再发下一次请求。WebSocket 则是在建立连接之后，客户端和服务端之间维持一个长期双向通道，服务端可以主动推送消息。

如果问配置中心为什么更常选长轮询，我会说主要是工程取舍问题。配置中心的核心诉求通常不是超高频实时消息，而是低频但可靠的配置通知。长轮询基于 HTTP，接入现有网关、负载均衡、代理体系都更简单，对企业网络环境兼容性也更好。相比之下，WebSocket 虽然实时性更强，但连接管理、状态维护、运维复杂度也会更高。

所以配置中心里很多时候长轮询已经够用了，它不是最炫的方案，但往往是复杂度和收益之间更平衡的方案。

分布式理论 & 限流

13. CAP、BASE理论；配置中心这类中间件如何做取舍？
CAP的意思是，在分布式系统里，一致性、可用性、分区容错性三者不能同时完全满足。实际系统里分区容错通常是没法放弃的，所以更多是在一致性和可用性之间做权衡。BASE 则更偏工程视角，强调系统不一定时刻强一致，但可以做到基本可用、允许软状态、最终一致。

如果结合配置中心这类中间件，我会说它通常是“写路径更偏一致性，读路径更偏可用性”。比如配置发布时，不能允许多个节点长期看到完全不一致的配置，否则风险很大，所以写入和发布过程要尽量保证一致性。但在读取侧，如果因为网络分区或者中心节点短暂异常就让业务系统完全拿不到配置，这个代价又太高，所以客户端通常会保留本地缓存、快照、副本机制，哪怕短时间读到旧配置，也比整个应用不可用更可接受。

所以我会把它总结成一句话：配置中心这类系统通常是在核心写操作上追求更强一致，在客户端读取侧接受有限的最终一致，以换取整体可用性。

14. 单机限流、对等节点集群限流、中心化限流(Redis)，三者优缺点分别是什么？
单机限流是最简单的，比如令牌桶、漏桶、滑动窗口这些直接在单机内存里做。它的优点是实现简单、性能高、没有外部依赖，适合保护单节点资源。缺点也很明显，就是它只能限制当前这台机器，做不到全局统一限流。

对等节点集群限流的思路是多个节点之间自己协同，不依赖单个中心。它的好处是没有明显的中心瓶颈，理论上扩展性更好，但实现会复杂很多，一致性、精度、节点间协调成本都比较难控制，所以真正落地难度不小。

中心化限流，比如基于 Redis 做全局计数，是实际项目里很常见的一种方案。它的优点是容易实现全局统一限流，规则比较集中，也方便按租户、接口、用户维度做统一配额控制。缺点是引入了中心依赖，Redis 本身要考虑高可用和性能瓶颈。

如果问我怎么选，我一般会说：只想保护单节点资源，用单机限流就够；如果要做租户级、接口级、全局统一配额，通常更适合 Redis 这类中心化限流；至于对等节点协同限流，更多是在超大规模、超高可用、对中心依赖特别敏感的场景下才会认真考虑。
