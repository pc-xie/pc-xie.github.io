面试

Java基础

JVM

1. 简述JVM内存区域划分，堆和元空间的区别？
JVM运行时数据区主要包括：程序计数器、虚拟机栈、本地方法栈、堆、方法区。

  • 程序计数器：记录当前线程执行字节码的位置，线程私有。
  • 虚拟机栈：存方法调用的栈帧，包含局部变量表、操作数栈等，线程私有。
  • 本地方法栈：给Native方法服务，线程私有。
  • 堆：存放对象实例和数组，是GC主要管理区域。
  • 方法区：存类元信息、常量、静态变量、JIT编译代码等。JDK8后方法区的实现主要是元空间。

堆和元空间区别：

  • 堆主要存对象实例。
  • 元空间主要存类元数据。
  • 堆在JVM内存中，元空间使用的是本地内存。
  • 堆溢出常见是 OutOfMemoryError: Java heap space，元空间溢出常见是 OutOfMemoryError: Metaspace。

2. Young GC、Full GC分别在什么条件触发？哪些情况对象会直接进入老年代？
Young GC通常发生在Eden区满的时候，回收年轻代对象。
Full GC一般是老年代空间不足、元空间不足、显示调用 System.gc()、CMS/G1某些回收失败等情况触发，代价高，通常会伴随更长停顿。

对象直接进入老年代的常见情况：

  • 大对象，超过 PretenureSizeThreshold。
  • 长期存活对象，经过多次Young GC后晋升。
  • Survivor区放不下，发生动态年龄判断或空间分配担保后晋升。
  • 老年代担保逻辑触发时，部分对象可能提前晋升。

3. 说说你排查GC问题的完整流程，会用到哪些工具？
我一般按“现象确认 -> 指标采集 -> 日志分析 -> dump定位 -> 参数调优”来做。

  1. 先看现象：接口RT抖动、吞吐下降、CPU飙高、Full GC频繁。
  2. 看监控：堆使用率、Young/Old区变化、GC频次、暂停时间、对象晋升速率。
  3. 分析GC日志：看是不是Young GC过频、Full GC过频、晋升失败、并发回收失败。
  4. 如果怀疑内存泄漏，导出heap dump看大对象和引用链。
  5. 结合业务判断，是短命对象过多、缓存失控、线程池任务堆积，还是不合理参数导致。
  6. 最后再调参数并回归验证。

常用工具：

  • jstat：看GC统计。
  • jmap：dump堆。
  • jcmd：综合诊断。
  • jstack：看线程状态。
  • MAT / VisualVM / JProfiler / Arthas：定位对象占用和热点代码。
  • GC日志分析工具：GCeasy 等。

如果结合简历里的GC优化项目，可以强调：
“我不是先调参数，而是先分清楚到底是内存泄漏还是正常高分配速率导致GC压力。”

4. Serializable是什么接口？serialVersionUID的作用？为什么它是标记接口？
Serializable 是Java的标记接口，本身没有方法，作用是告诉JVM：这个类允许被序列化。
serialVersionUID 用于标识序列化版本，一般用于反序列化时校验当前类版本和序列化时是否兼容。
如果类结构变了，而 serialVersionUID 不一致，反序列化会报错。

它设计成标记接口，是因为这里不需要调用方去实现具体方法，只需要一个“可序列化”的声明能力，序列化逻辑由JVM/ObjectOutputStream处理。

线程池

5. ThreadPoolExecutor有哪些核心参数？任务提交之后完整执行流程是什么？
核心参数：

  • corePoolSize：核心线程数
  • maximumPoolSize：最大线程数
  • keepAliveTime：非核心线程空闲存活时间
  • unit：时间单位
  • workQueue：阻塞队列
  • threadFactory：线程工厂
  • handler：拒绝策略

执行流程：

  1. 提交任务时，先看当前线程数是否小于核心线程数。
  2. 如果小于，就创建核心线程执行任务。
  3. 否则尝试把任务放入阻塞队列。
  4. 如果队列满了，再看线程数是否小于最大线程数。
  5. 如果小于，就创建非核心线程处理。
  6. 如果也到上限，就执行拒绝策略。

6. 线程池4种拒绝策略分别是什么，业务上如何选型？
JDK内置4种：

  • AbortPolicy：直接抛异常。
  • CallerRunsPolicy：调用者线程自己执行。
  • DiscardPolicy：直接丢弃。
  • DiscardOldestPolicy：丢弃队列中最老任务，再尝试提交。

选型看业务：

  • 核心链路、不能默默丢任务：一般选 AbortPolicy，配合告警。
  • 希望通过回压保护系统：可用 CallerRunsPolicy。
  • 允许部分任务丢失，如日志、埋点：可考虑 DiscardPolicy。
  • DiscardOldestPolicy 生产上相对少用，因为容易把排队中的旧任务悄悄丢掉，问题不直观。

7. 线程池使用无界队列会出现什么问题？为什么生产环境要用有界队列？
无界队列的问题：

  • 任务可以无限堆积，容易把内存打满。
  • 最大线程数形同虚设，因为任务一直先进队列，不会扩到 maximumPoolSize。
  • 系统表面平稳，实际上延迟会越来越高，最后可能OOM。

生产环境一般用有界队列，是为了：

  • 控制系统容量上限。
  • 提前暴露问题，而不是无限堆积。
  • 配合拒绝策略实现降级、限流、回压。

8. 线程池参数能不能直接网上抄模板？结合业务说说参数评估思路。
不能直接抄。线程池参数必须结合任务类型、响应时间目标、机器配置来定。
评估思路：

  • 先分CPU密集型还是IO密集型。
  • CPU密集型线程数一般接近CPU核数。
  • IO密集型可以适当放大，但不能无限大。
  • 队列长度要结合峰值流量、任务平均耗时、可接受排队时延。
  • 最大线程数要结合上下游承载能力，不是越大越好。
  • 最终要压测验证，不靠经验拍脑袋。

如果面试时结合项目可以说：
“比如网关里的鉴权、路由是短平快任务，线程数更偏保守；如果是配置中心异步推送或RPC聚合，更多要关注IO等待比例和下游熔断能力。”

Netty & IO

9. BIO、NIO、AIO三者区别，Netty为什么选择NIO/epoll模型？

  • BIO：同步阻塞，一个连接一个线程，连接多了线程成本高。
  • NIO：同步非阻塞，通过Selector多路复用，一个线程可以管理多个连接。
  • AIO：异步非阻塞，操作系统完成后回调通知。

Netty主要基于NIO，并在Linux下优先使用epoll，因为：

  • 连接数高时比BIO扩展性好很多。
  • Java生态里NIO成熟，兼容性强。
  • epoll适合高并发网络场景，减少空轮询和线程切换。
  • AIO在Java里落地并不如NIO生态成熟，所以Netty主流还是NIO/epoll。

10. Netty主从Reactor模型是什么？IO线程为什么不能执行业务耗时逻辑？
主从Reactor模型里：

  • Boss线程组负责接收连接。
  • Worker线程组负责读写事件处理。

这样做是为了职责分离，提高并发处理能力。

IO线程不能执行耗时业务逻辑，因为它的核心职责是处理网络事件。如果在IO线程里做数据库查询、远程调用、复杂计算，会阻塞事件循环，导致：

  • 其他连接读写被拖慢
  • RT抖动
  • 连接堆积甚至超时
    所以业务逻辑通常要投递到业务线程池处理。

11. Netty池化ByteBuf和非池化ByteBuf区别？ByteBuf内存泄漏如何检测？
区别：

  • 池化ByteBuf会复用内存块，减少频繁申请和释放，性能更好，适合高并发场景。
  • 非池化ByteBuf每次新建和释放，简单但开销更大。

Netty默认很多场景会优先使用池化，以降低GC和直接内存碎片问题。

内存泄漏检测：

  • 开启 ResourceLeakDetector。
  • 重点检查引用计数对象是否正确 release()。
  • 关注日志中是否有LEAK告警。
  • 排查自定义handler里是否持有ByteBuf但没释放。

12. 什么是零拷贝，Netty如何实现零拷贝？
零拷贝的核心目标是减少用户态和内核态之间不必要的数据复制，降低CPU开销，提高网络传输效率。

Netty里的零拷贝主要体现在：

  • sendFile / FileRegion：文件传输时减少数据拷贝。
  • CompositeByteBuf：逻辑上合并多个缓冲区，避免重新复制。
  • slice() / duplicate()：共享底层内存，只调整视图，不复制数据。

多线程

13. synchronized和Lock的区别？简述锁升级过程：偏向锁、轻量级锁、重量级锁。
synchronized 是Java内置关键字，语法简单，JVM层面实现。
Lock 是显式锁，典型是 ReentrantLock，功能更灵活，支持可中断、公平锁、超时获取、多个Condition。

区别主要是：

  • synchronized 自动加解锁，使用简单。
  • Lock 需要手动释放，但功能更丰富。
  • 高级并发场景下，Lock 更灵活。

锁升级过程：

  • 偏向锁：基本无竞争时，偏向某个线程，连CAS都尽量减少。
  • 轻量级锁：有线程竞争但不激烈，通过CAS自旋尝试获取。
  • 重量级锁：竞争激烈，自旋失败后升级为OS互斥量，线程阻塞挂起。

补一句：JDK新版本里偏向锁已经逐步弱化甚至移除，但面试里讲清这个历史机制就够了。

14. CompletableFuture如何处理异常？并行调用多个下游时如何处理单个任务失败？
异常处理常用：

  • exceptionally()：出现异常时兜底返回。
  • handle()：无论成功失败都处理。
  • whenComplete()：做结果回调，但不改变结果。

并行调用多个下游时，处理单个任务失败要看业务：

  • 如果允许部分失败，可以每个子任务单独兜底，最后聚合降级结果。
  • 如果必须全成功，可以用 allOf()，任一失败整体失败。
  • 更稳妥的做法是给每个任务单独设置超时、异常转换、默认值，避免一个下游把整个聚合请求拖死。

如果结合社招场景可以答：
“聚合接口里我通常不会让单个下游异常直接打穿全链路，而是做超时隔离、异常兜底和部分结果返回。”

MySQL数据库

1. MySQL四大事务隔离级别分别是什么，各自解决什么问题？
四个隔离级别：

  • Read Uncommitted：能读到未提交数据，可能脏读。
  • Read Committed：只能读已提交数据，解决脏读，但可能不可重复读。
  • Repeatable Read：同一事务内多次读结果一致，解决不可重复读。MySQL默认这个级别。
  • Serializable：最高隔离，串行执行，解决幻读，但并发性能最差。

一般理解：

  • RU解决最少，并发最高。
  • RC是很多数据库默认级别。
  • RR是InnoDB默认。
  • Serializable用于极少数强一致要求场景。

2. MVCC实现原理是什么？undo log、ReadView作用？RC与RR的ReadView有什么差异？
MVCC是多版本并发控制，核心是让读操作尽量不加锁，通过“版本链 + 可见性判断”实现一致性读。

undo log 的作用：

  • 更新数据时保留旧版本，形成版本链。
  • 回滚时也要用到。

ReadView 的作用：

  • 判断当前事务能看到哪个版本的数据。
  • 本质上是基于事务ID做可见性判断。

RC和RR差异：

  • RC下，每次执行快照读都会生成新的ReadView，所以可能前后读到不一样的数据。
  • RR下，一个事务通常只在第一次快照读时生成ReadView，后续复用，所以多次读结果一致。

3. 什么是快照读、当前读？哪些SQL属于当前读？
快照读就是普通 select，读的是MVCC里满足可见性规则的历史版本，一般不加锁。
当前读是读最新版本，并且通常要加锁，目的是保证接下来更新时数据一致。

当前读常见SQL：

  • select ... for update
  • select ... lock in share mode / 新语法 for share
  • update
  • delete
  • insert

4. InnoDB行锁什么情况下会退化为表锁？意向锁的作用是什么？
严格说很多场景不是“退化”为表锁，而是因为没走索引或扫描范围过大，锁住大量记录，看起来像表锁效果。
典型情况：

  • 更新条件没有命中索引，导致全表扫描，加锁范围极大。
  • 某些情况下Next-Key Lock覆盖范围很大。

意向锁作用：

  • 表示“某个事务准备对某些行加锁”。
  • 让表锁和行锁之间快速判断是否冲突，不需要逐行检查。
  • 意向共享锁IS、意向排他锁IX，本质是提高加表锁时的冲突判断效率。

5. redo log、undo log、binlog分别的作用，三者区别？

  • redo log：保证事务持久性，崩溃恢复时把已提交但未刷盘的数据重做出来，是InnoDB引擎层日志。
  • undo log：保存旧版本，用于事务回滚和MVCC。
  • binlog：记录逻辑操作日志，主要用于主从复制和数据恢复，是Server层日志。

区别：

  • redo是物理日志，偏存储恢复。
  • undo是逻辑上的反向信息，偏回滚和多版本。
  • binlog是逻辑日志，偏复制和归档。

6. 事务ACID四个特性分别依靠什么来实现？

  • 原子性 Atomicity：通过 undo log 保证，失败可回滚。
  • 一致性 Consistency：靠原子性、隔离性、持久性，以及业务约束共同保证。
  • 隔离性 Isolation：通过锁机制和MVCC实现。
  • 持久性 Durability：通过 redo log 保证，提交后即使宕机也能恢复。

7. 慢SQL排查思路，索引失效常见场景有哪些？
排查思路：

  1. 先定位具体SQL，结合慢日志、监控、APM。
  2. 用 EXPLAIN 看执行计划。
  3. 关注是否走索引、扫描行数、回表次数、排序和临时表。
  4. 看SQL写法是否合理，是否需要联合索引、覆盖索引。
  5. 判断是单条SQL问题，还是数据量增长、统计信息失准、锁等待问题。

索引失效常见场景：

  • 对索引列做函数运算、表达式计算。
  • 隐式类型转换。
  • 联合索引不满足最左前缀。
  • like '%xx' 前缀模糊匹配。
  • or 使用不当。
  • 区分度太低，优化器判断全表扫描更划算。
  • 范围查询后，联合索引后续列利用受限。

8. 大表数据持续膨胀，如何做冷热数据归档？
常见做法：

  • 按时间维度做冷热分层，比如近3个月热数据保留在线表，历史数据归档到冷表。
  • 归档时用定时任务批量迁移，避免大事务。
  • 归档表可放低频库、低成本存储，甚至ES/Hive/对象存储。
  • 应用层路由查询，或者通过视图/中间层屏蔽冷热表差异。
  • 删除热表历史数据时要分批，避免长事务和主从延迟。

如果结合配置中心或网关项目，可以说：
“像配置变更记录、审计日志、网关访问日志都适合按时间归档，在线库只保留高频查询数据。”

9. 并发更新同一条记录，如何防止数据丢失覆盖，乐观锁怎么实现？
常见方式：

  • 悲观锁：select ... for update，串行化更新。
  • 乐观锁：基于版本号或更新时间字段。
  • CAS思想：更新时带上旧版本条件。

乐观锁实现示例：
先查出 version=5，更新时执行：
update table set value=?, version=6 where id=? and version=5
如果影响行数为0，说明有并发修改，当前更新失败，再重试或返回冲突。

乐观锁适合读多写少、冲突不频繁场景；悲观锁适合强一致、高冲突更新场景。

10. 分库分表适用什么场景，什么场景不需要分库分表，参考你的配置中心项目。
适用场景：

  • 单表数据量特别大，索引维护成本高。
  • 并发写入特别高，单机存储或IO成为瓶颈。
  • 需要水平扩展。

不需要分库分表的场景：

  • 数据量和QPS远没到单库瓶颈。
  • 业务更关注一致性和复杂查询。
  • 团队对分布式事务、跨分片查询、扩容迁移没有足够治理能力。

如果结合配置中心项目可以答：
“配置中心核心数据量通常没大到必须分库分表，更多瓶颈在长轮询连接、推送链路和本地缓存，而不是数据库容量本身。所以优先做缓存、读写分离、归档、索引优化，只有规模真的上来才考虑拆分。”

中间件 & 网络技术基础

Zookeeper

1. ZAB协议的核心作用是什么？
ZAB是ZooKeeper的原子广播协议，核心作用是：

  • 保证分布式场景下数据的一致性。
  • 保证Leader崩溃恢复后，集群仍然能按顺序提交事务。

它主要解决的是崩溃恢复 + 消息广播顺序一致的问题。

2. ZK的节点类型：持久、临时、顺序节点，各自适用场景？

  • 持久节点：客户端断开后仍存在，适合配置数据、注册元信息。
  • 临时节点：客户端会话断开后自动删除，适合服务注册、存活探测。
  • 顺序节点：创建时自动追加递增序号，适合分布式锁、队列、选主辅助。

常见组合：

  • 临时顺序节点经常用来实现分布式锁或选举。

3. ZK Watcher机制是什么？Watcher一次性触发，如何解决？
Watcher是ZooKeeper的事件通知机制，客户端对节点注册监听后，节点变化会收到通知。
它是一次性触发的，触发后如果还要继续监听，客户端需要重新注册。

解决方式：

  • 客户端收到事件后重新注册Watcher。
  • 业务层做本地缓存 + 增量刷新。
  • 如果需要更稳定的监听封装，通常用Curator这类客户端框架做自动重注册。

4. ZK适合做哪些事情，不适合做哪些事情？
适合：

  • 服务注册发现
  • 配置管理
  • 分布式锁
  • Leader选举
  • 命名服务

不适合：

  • 大数据量存储
  • 高频大流量读写
  • 复杂查询
  • 当消息队列用
    因为ZK更适合存小而关键的协调数据，不适合承载重数据业务流量。

RPC(Dubbo、gRPC)

5. Dubbo完整调用流程，底层网络组件、常见序列化方案？
典型流程：

  1. 服务提供者启动并注册到注册中心。
  2. 消费者订阅服务地址。
  3. 消费者本地生成代理对象。
  4. 发起调用时经过负载均衡选择一个提供者。
  5. 通过网络客户端发请求。
  6. 服务端反序列化、执行业务逻辑。
  7. 结果序列化后返回给消费者。

底层网络组件常见是Netty。
常见序列化方案有Hessian2、Kryo、Protobuf、Fastjson2等，不同版本和框架支持不同。

6. Dubbo有哪几种负载均衡策略？
常见策略：

  • Random：随机，默认较常见。
  • RoundRobin：轮询。
  • LeastActive：最少活跃调用数。
  • ConsistentHash：一致性哈希。

选型一般看场景：

  • 通用场景用随机。
  • 请求耗时差异大时最少活跃更合理。
  • 有会话粘性诉求可用一致性哈希。

7. gRPC和Dubbo的主要差异？
主要差异：

  • gRPC更偏跨语言、标准化，基于HTTP/2和Protobuf。
  • Dubbo更偏Java生态和微服务治理能力。
  • gRPC在多语言互通、流式通信上优势明显。
  • Dubbo在服务治理、注册发现、路由、容错等企业级能力上更成熟。

一句话总结：
gRPC偏“高性能跨语言RPC框架”，Dubbo偏“面向Java微服务治理的RPC框架”。

8. RPC调用的超时与重试，有哪些坑需要注意？
主要坑点：

  • 超时设置过大，故障扩散慢。
  • 超时设置过小，正常抖动也被误判失败。
  • 重试没有幂等保障，导致重复下单、重复扣费。
  • 多层服务都重试，造成重试风暴。
  • 请求本身已经在服务端执行成功，但客户端超时后又重试，造成数据重复。

实践上通常要：

  • 区分连接超时、读取超时。
  • 只对幂等读操作谨慎重试。
  • 设置重试次数上限和退避策略。
  • 配合熔断、限流、降级。

TCP / HTTP网络

9. TCP三次握手、四次挥手；TIME_WAIT、CLOSE_WAIT产生的原因，网关场景如何优化？
三次握手目的是双方确认收发能力并同步初始序列号。
四次挥手是因为TCP全双工，双方关闭连接通常要分别发送FIN和ACK。

TIME_WAIT：主动关闭连接的一方在发送最后ACK后进入，目的是确保对方收到ACK，并让旧报文自然消失。
CLOSE_WAIT：被动关闭方收到FIN后进入，说明本地还没真正调用close，通常是应用没及时释放连接。

网关场景优化：

  • 尽量使用连接复用、长连接，减少频繁建连。
  • 调整连接池和keepalive策略。
  • 排查应用是否存在连接未及时关闭导致CLOSE_WAIT堆积。
  • 合理调内核参数，但根本还是优化应用层连接管理。

10. HTTP1.1 和 HTTP2 的区别，网关场景HTTP2带来哪些收益？
HTTP/1.1特点：

  • 长连接
  • 管道化理论支持但实际有限
  • 文本协议
  • 同一连接请求容易队头阻塞

HTTP/2特点：

  • 二进制分帧
  • 多路复用
  • 头部压缩
  • 支持服务端推送（实际应用不多）

网关场景收益：

  • 一个连接并发多个请求，减少连接数。
  • 降低握手和TLS开销。
  • 提升弱网或高并发下的传输效率。
  • 对移动端和跨地域访问效果更明显。

11. TCP滑动窗口、拥塞控制简单说明。
滑动窗口用于流量控制，接收方通过窗口大小告诉发送方自己还能接收多少数据，避免发送过快。
拥塞控制是为了避免网络被打爆，发送方根据网络状况动态调整发送速率。

常见拥塞控制过程：

  • 慢启动
  • 拥塞避免
  • 快重传
  • 快恢复

前者解决“接收方吃不消”，后者解决“网络吃不消”。

12. 长轮询和WebSocket的区别，配置中心为什么选用长轮询？
长轮询是客户端发请求后，服务端如果没数据就挂起，直到超时或有变更再返回，客户端再发下一次。
WebSocket是建立持久双向连接，服务端可以主动推送。

配置中心常选长轮询，原因通常是：

  • 实现简单，基于HTTP，容易接入现有网关和负载均衡。
  • 对代理、企业网络环境兼容性更好。
  • 配置变更频率通常不高，长轮询已经够用。
  • 相比WebSocket，连接管理和状态维护复杂度更低。

如果结合项目可以说：
“配置中心的核心诉求不是高频实时消息，而是低频可靠通知，所以长轮询在复杂度和收益之间更平衡。”

分布式理论 & 限流

13. CAP、BASE理论；配置中心这类中间件如何做取舍？
CAP指分布式系统在一致性、可用性、分区容错性之间不能三者同时完全满足，分区容错通常是必须接受的，所以更多是在C和A之间权衡。

BASE强调：

  • Basically Available：基本可用
  • Soft state：软状态
  • Eventually consistent：最终一致性

配置中心取舍一般是：

  • 配置发布时更偏一致性，不能新旧版本混乱太久。
  • 配置读取时更偏可用性，本地缓存和快照要顶上。
  • 网络分区时宁可短时间返回旧配置，也不能整个应用不可用。

所以实际通常是：核心写入保证强一致，客户端读取侧接受短暂最终一致。

14. 单机限流、对等节点集群限流、中心化限流(Redis)，三者优缺点分别是什么？
单机限流：

  • 优点：实现简单、性能高、无外部依赖。
  • 缺点：只能限制单节点，不适合多实例全局统一限流。

对等节点集群限流：

  • 优点：不依赖单中心，扩展性较好。
  • 缺点：实现复杂，一致性和精度不好控制，节点间协同成本高。

中心化限流，比如Redis：

  • 优点：容易实现全局限流，规则统一。
  • 缺点：引入中心依赖，Redis可能成为性能瓶颈或单点，需要高可用设计。

业务上怎么选：

  • 单机保护本节点，用单机限流。
  • 需要租户级、接口级全局配额，通常用Redis中心化限流。
  • 超大规模、多地域、极致高可用场景，才会考虑更复杂的分布式协同方案。
